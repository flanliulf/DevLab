## Q1. Apple Continuity（Universal Clipboard / AirDrop / iCloud Drive）能否跨远程网络用？

### Takeaway
Universal Clipboard 和 AirDrop 都是近距离功能（BLE 发现 + Apple 点对点 Wi-Fi），不走路由、不走 Tailscale，只有两台 Mac 物理上在一起时才可用；iCloud Drive 任何地方都能用，但同步延迟不可控，且 "Optimize Mac Storage" 会把 `.git` 等文件驱逐成占位符，不适合放 git 仓库或 node_modules。

### Cited Findings
**Universal Clipboard**
- Apple 官方要求：各设备登录同一 Apple Account；蓝牙和 Wi-Fi 都打开；Handoff 打开（默认开）；设备"彼此靠近"（near each other）。复制的内容只在另一台设备上保留一小段时间，或直到任一设备再复制别的内容。— [Apple Support 102430](https://support.apple.com/en-us/102430)
- Apple 这篇文档没有提到任何远程/跨网络用法，只描述近距离场景。— [Apple Support 102430](https://support.apple.com/en-us/102430)
- 第三方故障排查文章：Universal Clipboard 是近距离功能，不是远距离同步；一台在蜂窝数据上，或在阻止本地互连的访客网络里，复制内容就过不去。— [Octoclip](https://octoclip.app/learn/universal-clipboard-not-working/)（第三方，非 Apple）
- Apple 开发者论坛有"睡眠后 Universal Clipboard 失效"的报告（说明它依赖设备唤醒状态和近距离广播）。— [Apple Developer Forums 704153](https://developer.apple.com/forums/thread/704153)（仅看到标题）

**AirDrop**
- 传输机制：先用 Bluetooth Low Energy（BLE）广播发现设备，再用"Apple 自研的点对点 Wi-Fi"传输；连接用 TLS 加密；"Wi-Fi 无线电直接在设备之间通信，不经过互联网连接或无线接入点（AP）"。— [Apple Platform Security：AirDrop security](https://support.apple.com/guide/security/airdrop-security-sec2261183f4/web)
- 身份：每个用户在设备上有 2048 位 RSA 身份；发现时广播基于 Apple Account 邮箱/手机号的 "AirDrop short identity hash"；"仅限联系人"模式下接收方用通讯录哈希比对。— [Apple Platform Security：AirDrop security](https://support.apple.com/guide/security/airdrop-security-sec2261183f4/web)

**iCloud Drive**
- 如果用 iCloud Drive 同步 ~/Documents 并打开 "Optimize Mac Storage"，磁盘快满时 macOS 会静默把本地文件驱逐成 "dataless placeholders"，`.git` 目录也不例外。— [DEV Community (ombak)](https://dev.to/ombak/many-mac-developers-misunderstand-does-icloud-secretly-ignore-git-files-the-reality-is-much-3970)
- `.git` 下有成千上万个小对象文件、refs、pack、lock、log；再加上 node_modules / venv / 构建缓存，iCloud 的同步队列可能一直收敛不了；建议把项目放在 `~/Developer` 等非 iCloud 目录，以 git remote 作为真正的备份。— [LSyncer Blog](https://lsyncer.syntanea.com/blog/git-repository-icloud-drive/)（注意：这是一个同步工具厂商的博客，有推销动机）
- 有专门讲"macOS iCloud 让 Node.js 应用崩溃"的 2026 年开发者文章，也说明这个坑在 2026 年仍然存在。— [rentierdigital 2026](https://rentierdigital.xyz/blog/fix-macos-icloud-nodejs-crashes)（只看到标题和摘要）

### Inferences
- 在家/办公室两台机器同处一室时，Universal Clipboard 可以当"零配置"的文本/图片剪贴板桥用（前提是两台 Mac 同一 Apple Account）；人一出门就失效，所以不能作为主通道。host 若是专门给 agent 用、另建了 Apple Account 或没登录 Apple Account，Universal Clipboard 和 AirDrop（Contacts Only 模式）都会不可用或受限。
- AirDrop 不经过 AP，所以一定不走 Tailscale（Tailscale 是 IP 层覆盖网络）。
- iCloud Drive 可以用来放"非代码"的小文件（截图、PDF spec），但不应放 git 仓库或 agent 工作目录；如果 host 打开了 Desktop & Documents 同步，agent 在 ~/Documents 下 clone 仓库有被驱逐的风险。

### Gaps
- 没能打开 Apple Platform Security 的 Handoff/Universal Clipboard 技术细节页（BLE/点对点 Wi-Fi、加密、保留时长的确切数值），Apple 公开文档只写了"briefly"。
- 没找到 Apple 对 macOS 26 下 Continuity 行为有任何改动的官方说明。
- 没找到 iCloud Drive 同步延迟的量化数据。

## Q2. Tailscale 原生通道：Taildrop（`tailscale file`）与 Taildrive（WebDAV 共享）

### Takeaway
Taildrop 适合一次性发文件（加密、点对点，macOS 接收端落到 ~/Downloads），但截至 2026-09 仍是 public alpha，只能在"自己名下的个人设备"之间用，被打了 tag 的节点不能用。Taildrive 截至 2026-09 仍是 alpha：在 `100.100.100.100:8080` 上提供 WebDAV，macOS 需要 `defaults write` 才能显示共享选项，另外还要在策略里配置 nodeAttrs 和 grants。

### Cited Findings
**Taildrop**
- 状态：public alpha，所有套餐可用；需要在管理后台 General 设置中打开 **Send Files**。— [Tailscale KB 1106 Taildrop](https://tailscale.com/kb/1106/taildrop)
- 传输走加密的点对点连接，用"最快可用路径"。— [Tailscale KB 1106](https://tailscale.com/kb/1106/taildrop)
- 限制：只能在"你自己的个人设备"之间发送；不能发给别的用户的设备；"不能用 Taildrop 在你打了 tag 的节点之间收发"。— [Tailscale KB 1106](https://tailscale.com/kb/1106/taildrop)
- macOS 上收到的文件落在 `~/Downloads`。— [Tailscale KB 1106](https://tailscale.com/kb/1106/taildrop)
- 失败的传输在大多数平台上 1 小时内可以续传，但 **macOS 和 iOS 作为接收端不支持续传**。— [Tailscale KB 1106](https://tailscale.com/kb/1106/taildrop)
- 文档没有写文件大小上限。— [Tailscale KB 1106](https://tailscale.com/kb/1106/taildrop)
- CLI：`tailscale file cp <files> <target>:`，参数有 `--name`（文件从 stdin `-` 读入时尤其有用）、`--targets`（列出可发送的目标）、`--verbose`；`tailscale file get <dir>` 把文件从收件箱移出，参数有 `--wait`、`--loop`（循环接收）、`--conflict=skip|overwrite|rename`。— [Tailscale CLI KB 1080](https://tailscale.com/kb/1080/cli)

**Taildrive**
- 状态："Taildrive is currently in alpha"。— [Tailscale KB 1369 Taildrive](https://tailscale.com/kb/1369/taildrive)
- 机制：Tailscale 客户端内置 WebDAV 服务，地址 `100.100.100.100:8080`；每个共享的路径是 `/<tailnet>/<machine>/<share>`。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- 平台：Linux、macOS、Windows、Synology（DSM 7）可以共享；iOS/Android 只能访问。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- macOS 默认隐藏 File Sharing 选项。App Store 版执行 `defaults write io.tailscale.ipn.macos FileSharingConfiguration -string show`，官网独立版执行 `defaults write /Users/$(whoami)/Library/Preferences/io.tailscale.ipn.macsys.plist FileSharingConfiguration show`，然后重启 Tailscale 应用。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- 策略：nodeAttrs 里要有 `drive:share` 和 `drive:access`；grants 里用 `tailscale.com/cap/drive`，写明 `shares` 和 `access`（`rw`/`ro`）。示例：`{"target":["autogroup:member"],"attr":["drive:share","drive:access"]}`，以及 `{"src":["*"],"dst":["*"],"app":{"tailscale.com/cap/drive":[{"shares":["*"],"access":"rw"}]}}`。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- macOS 挂载方法：Finder → Connect to Server（⌘K）→ 输入 `http://100.100.100.100:8080` → 选 Guest → 接受"不安全连接"提示。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- 其他限制：别人共享进你 tailnet 的设备不能访问 Taildrive；rclone 配合 1.64.2 及更早的客户端需要加 `--inplace`。— [KB 1369](https://tailscale.com/kb/1369/taildrive)
- CLI 有 `tailscale drive share|rename|unshare|list`。— [Tailscale CLI KB 1080](https://tailscale.com/kb/1080/cli)；KB 1369 写的是 CLI 适用于 Windows/Linux/Synology，macOS 用 GUI。— [KB 1369](https://tailscale.com/kb/1369/taildrive)

### Inferences
- **与 host 配置的冲突**：常见做法是给常开的 host 打 `tag:server` 之类的 tag（这样能关闭 key 过期、用 ACL 管理）。但打了 tag 之后 Taildrop 就不能用了。如果要用 Taildrop，host 必须保持为"用户自己的设备"（不打 tag）。
- Taildrop 适合"laptop → host 发一张截图或 spec"：`tailscale file cp shot.png host:`，然后在 host 上 `tailscale file get --conflict=rename ~/inbox`（或者让 GUI 落到 ~/Downloads），再把路径贴给 agent。反方向（host 上 agent 生成的产物 → laptop）同理。
- 按 Tailscale 文档的描述推断，Taildrive 的延迟和吞吐受"WebDAV + Finder"组合限制，适合浏览或取文件，不适合在上面跑 git/npm（macOS WebDAV 客户端对大量小文件很慢，这是一般经验，未找到针对 Taildrive 的基准数据）。
- Taildrive 以 Guest 身份、经"未加密 HTTP"连接到 100.100.100.100。这个地址是本机 Tailscale 进程提供的，实际跨机流量走 WireGuard 加密；访问控制依赖 grants，不依赖 macOS 账户密码。

### Gaps
- Taildrop 是否会经 DERP 中继兜底（当无法建立直连时）、单文件大小的实际上限：KB 未说明。
- Taildrop / Taildrive 在 macOS 26 上的已知 bug：未找到专门报告。
- Taildrive 的性能基准（小文件/大文件吞吐）：未找到。

## Q3. 持续同步：Syncthing / Mutagen / Unison

### Takeaway
Syncthing（v2，2026-02 起的正式版本）适合做一个"交换目录"（截图、日志、产物），连续、点对点、LAN 与 Tailscale 都能用，但有约 10 秒的聚合延迟，冲突时生成 `.sync-conflict` 副本，不适合两边同时编辑的 git 工作树。Mutagen 是专为开发设计的双向同步，有明确的冲突模式和 VCS 忽略，但最后一个版本是 2025-02 的 v0.18.1，Docker 收购后独立版本更新变慢。Unison 2.53.8（2025-11）仍在维护，但 macOS 上的文件监听需要第三方 adapter。

### Cited Findings
**Syncthing**
- 官方 macOS 应用（syncthing-macos）：自 2026-02-23 起 v2 是受支持版本；v1 已弃用，不再更新；v2 需要 macOS 12+；安装：`brew install --cask syncthing-app`；提供 universal binary（支持 Apple silicon）；日志在 `~/Library/Application Support/Syncthing/`；警告"确保没有其他 syncthing 实例或包装器在运行"。— [syncthing-macos README (v2)](https://github.com/syncthing/syncthing-macos/blob/v2/README.md)
- 最新稳定版 2.1.5（2026-09-08）— 搜索摘要，未在原始发布页核对。— [Syncthing 论坛：Syncthing for macOS v2.0](https://forum.syncthing.net/t/syncthing-for-macos-v2-0/25380)
- 冲突：两台设备同时修改同一文件且内容不同时，修改时间较旧的那份会被重命名为 `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`；时间相同时，按设备 ID 前 63 位较大的一方标为冲突；冲突文件之后被当作普通文件同步到所有设备。— [Syncthing docs: syncing.rst](https://raw.githubusercontent.com/syncthing/docs/main/users/syncing.rst)（对应 docs.syncthing.net/users/syncing.html）
- 大小写：Syncthing 内部路径区分大小写；在不区分大小写的文件系统上（Windows、macOS、Android），同一路径的两种大小写变体无法共存，会报 "case conflict"，需要人工统一命名。— [syncing.rst](https://raw.githubusercontent.com/syncthing/docs/main/users/syncing.rst)
- 延迟：文件监听器把变更"累积 10 秒"再处理（`fsWatcherDelayS`），删除操作再额外延迟 1 分钟；完整扫描默认每小时一次，间隔在 3/4 到 5/4 之间随机。— [syncing.rst](https://raw.githubusercontent.com/syncthing/docs/main/users/syncing.rst)
- 临时文件 `.syncthing.<name>.tmp`，出错时最多保留一天。— [syncing.rst](https://raw.githubusercontent.com/syncthing/docs/main/users/syncing.rst)
- 忽略规则写在 `.stignore`，是 glob 模式。— [Syncthing FAQ usage](https://raw.githubusercontent.com/syncthing/docs/main/users/faq-parts/usage.rst)
- 扩展属性：`syncXattrs` / `sendXattrs` 自 1.22.0 起支持 Linux、macOS、FreeBSD、NetBSD；对端必须开启其中之一才会应用 xattr；扫描 xattr 可能拖慢扫描速度。— [Syncthing docs: syncXattrs](https://docs.syncthing.net/advanced/folder-sync-xattrs.html)

**Mutagen**
- 同步模式：`two-way-safe`（默认，只有不会丢数据时才自动解决冲突）、`two-way-resolved`（alpha 端自动赢所有冲突）、`one-way-safe`（只允许 alpha→beta，同时保护 beta 上的修改）、`one-way-replica`（beta 成为 alpha 的精确副本，beta 上多出或修改的内容立即被覆盖或删除）；用 `-m/--sync-mode` 指定；第一个端点是 alpha，第二个是 beta。— [Mutagen docs: synchronization](https://mutagen.io/documentation/synchronization)
- 冲突只出现在 `two-way-safe` 和 `one-way-safe` 模式中；解决方法是删除你希望输掉的一端的内容。— [Mutagen docs: synchronization](https://mutagen.io/documentation/synchronization)
- 监听：`portable`（默认，按平台选最高效的实现）、`force-poll`、`no-watch`（只在 `mutagen sync flush` 时同步）；macOS 上在同步根目录建一个原生递归 watch，并加上廉价轮询检查根目录是否被删除或重建；默认轮询间隔 10 秒（`--watch-polling-interval`）；Linux/BSD 需要给每个文件或目录分配 watch 描述符，node_modules 这类目录很容易耗尽配额。— [Mutagen docs: watching](https://mutagen.io/documentation/synchronization/watching)
- 版本：最新 v0.18.1（2025-02-24，修复与 Docker Engine 28 的兼容）；v0.18.0（2024-10-24）加入 `.dockerignore` 风格的忽略语法，并改进 macOS 上 FAT32/ExFAT 的可执行位检测。截至调研时没有更新的版本。— [mutagen-io/mutagen releases](https://github.com/mutagen-io/mutagen/releases)
- Docker 于 2023-06-27 收购 Mutagen，并把它集成进 Docker Desktop，做成 "Synchronized file shares"（宣称文件操作快 2–10 倍）。— [Docker blog: Mutagen acquisition](https://www.docker.com/blog/mutagen-acquisition/)；[Docker: Synchronized File Shares](https://www.docker.com/blog/announcing-synchronized-file-shares/)

**Unison**
- 最新稳定版 2.53.8（2025-11-05）；2.53.7 起不再安装 `fsmonitor.py`。— 搜索摘要，来源 [Wikipedia: Unison](https://en.wikipedia.org/wiki/Unison_(software))；发布页 [bcpierce00/unison releases](https://github.com/bcpierce00/unison/releases)
- Unison 自带 Linux 和 Windows 的文件监听 adapter，**没有 macOS 的**；第三方 Go 版 `unison-fsmonitor` 支持 macOS。— [benesch/unison-fsmonitor](https://github.com/benesch/unison-fsmonitor)
- 要求两端 Unison 版本和 OCaml 编译版本匹配：这是一般经验，本轮未找到可引用的来源，列入 Gaps。

### Inferences
- **推荐的分工**：代码仓库以 **git 为唯一真相**（host 上的 agent 在各自的 worktree 里工作，laptop 用 `git fetch` 或直接 SSH 进 host 查看），**不要**让 Syncthing/Mutagen 双向同步正在被 agent 修改的 `.git`。同步工具只用于：① `~/Exchange`（截图、spec、日志）交换目录；② 必要时用 `one-way-replica` 把 host 的构建产物或日志目录单向镜像到 laptop。
- Syncthing 的 10 秒聚合延迟加上冲突副本机制，对"丢一张截图过去"已经够快；但对"两边同时编辑同一文件"会产生 `.sync-conflict` 副本，git 工作树里就会出现垃圾文件。
- Mutagen 的 `--ignore-vcs` 和 `two-way-resolved` 比较适合"laptop 上编辑 → host 上构建"的单一编辑者流程。按 Mutagen 的一般用法，它通过 SSH 在远端安装 agent 二进制，所以要求 host 开启 Remote Login，并且 laptop 的 `~/.ssh/config` 能直接 `ssh host`（包括 Tailscale MagicDNS 名）。这一点来自对 Mutagen 的一般了解，本轮未打开 transports 文档核对。
- 由于 Mutagen 自 2025-02 以后没有新版本，在 macOS 26/27 上使用前应自测；Syncthing v2 的维护更活跃。
- macOS 特有：两台 Mac 都是默认的不区分大小写 APFS，所以两者之间不容易出 case conflict；但如果仓库是在 Linux 上建的、含有只差大小写的文件名，那么 git 本身在 Mac 上就已经会出问题。
- xattr：Syncthing 默认不同步 xattr，所以 Finder 标签、`com.apple.quarantine` 等不会随文件过去（这对"被隔离的下载文件"反而是好事，但会丢失标签）。

### Gaps
- Syncthing v2 在 macOS 26 上的 TCC 行为（访问 ~/Desktop、~/Documents 等受保护目录时是否弹窗、需要授予哪个进程）：没有找到官方说明。
- Syncthing / Mutagen 在含大型 node_modules 的仓库上的扫描时间基准：没有找到可引用的数据。
- Mutagen 在 macOS 26 上是否有已知问题：没有找到。
- Unison 两端版本匹配要求：未找到引用来源。

## Q4. 网络挂载：SMB / SSHFS（macFUSE vs FUSE-T）/ NFS / rclone，以及在挂载盘上跑 git/node 的风险

### Takeaway
在 LAN 或 Tailscale 上用 macOS 自带的 SMB 文件共享挂载 host 最简单，用于"用 Finder 浏览、取文件"没问题，但**不要在网络挂载上跑 git、npm 或 agent**（git 的 fsmonitor 默认拒绝网络挂载，小文件 IO 很慢）。SSHFS 在 2026 年有两条免 kext 的路：FUSE-T（NFS/SMB 后端，macOS 26+ 还有 FSKit 后端）和 macFUSE 5 的 FSKit 后端（`-o backend=fskit`，只能挂在 /Volumes 下，性能不如 kext 后端，macOS 26.6.2 上有报告失败的 issue）。rclone 在 macOS 上官方推荐用 `rclone nfsmount`。

### Cited Findings
**macOS SMB 文件共享**
- 开启路径：Apple 菜单 > System Settings > General > Sharing > File Sharing；点 "+" 添加共享文件夹；按用户设置 Read & Write / Read Only / Write Only (Drop Box) / No Access；高级选项里有 "Only allow SMB encrypted connections"；文档版本选择器包含 macOS Tahoe 26，但没有 26 专属的差异。— [Apple Mac User Guide: Set up file sharing](https://support.apple.com/guide/mac-help/set-up-file-sharing-on-mac-mh17131/mac)
- .DS_Store 会拖慢 SMB（Finder 在访问过的每个子目录里写入隐藏文件）；可以用 `defaults write com.apple.desktopservices DSDontWriteNetworkStores -bool TRUE` 禁止在网络卷上写。— 搜索摘要，对应 [Cornell IT: macOS and CIFS performance tips](https://it.cornell.edu/shared-file/apple-macos-and-cifs-performance-troubleshooting-tips)
- 有用户报告在远程经 WireGuard/Tailscale 上传 SMB 极慢（Unraid 论坛，非 macOS host）。— [Unraid forum](https://forums.unraid.net/topic/190475-extremely-slow-smb-upload-via-remote-with-wireguard-andor-tailscale/)；Tailscale 上也有"连接时所有流量变慢"的 issue。— [tailscale/tailscale #8524](https://github.com/tailscale/tailscale/issues/8524)（两者都只看到标题和摘要，属于个例）

**macFUSE**
- 两个后端：默认的 VFS（kernel extension）后端，以及 macOS 15.4 起可用的 FSKit 后端，挂载时加 `-o backend=fskit` 选择。— [macFUSE wiki: FUSE Backends](https://github.com/macfuse/macfuse/wiki/FUSE-Backends)
- FSKit 后端的限制：不支持 /Volumes 以外的挂载点；文件总是以读写模式打开；还不支持 FUSE notification API；拿不到 context 信息；大多数原本由内核处理的挂载选项还没实现；"FSKit 卷的 I/O 性能不及 kext 后端"。— [macFUSE wiki: FUSE Backends](https://github.com/macfuse/macfuse/wiki/FUSE-Backends)
- 截至 2026-09 的最新版本是 macFUSE 5.4.0；有了 FSKit 后端，在 macOS 26 上不必再进 Recovery 模式降低安全等级来加载 kext — 搜索摘要，来源 [macfuse.github.io](https://macfuse.github.io/)，未打开原文核对版本号。
- 已知问题：issue 标题为"FSKit backend: fskitd does not report `macfuse-local` module on macOS 26.6.2 and 27.0 beta (extension registered and enabled)"。— [macfuse/macfuse #1192](https://github.com/macfuse/macfuse/issues/1192)（只看到标题）
- macFUSE 官方分发的 SSHFS 最新版是 3.7.5，要求 macFUSE 4.10+，支持 Apple silicon 和 Intel，由 Benjamin Fleischer 的 Developer ID 签名；wiki 没有提到 FSKit 后端支持。— [macFUSE wiki: SSHFS](https://github.com/macfuse/macfuse/wiki/File-Systems-%E2%80%90-SSHFS)

**FUSE-T**
- 免 kext 的 FUSE 实现，在用户态运行，通过本地服务器接入 macOS 的挂载流程；支持三种后端：NFS、SMB，以及 **macOS 26 及以后的原生 FSKit**；兼容 libfuse2 和 libfuse3；安装：`brew install macos-fuse-t/homebrew-cask/fuse-t`；个人使用免费，嵌入到产品中需要商业授权；当前版本 1.2.0。— [fuse-t.org](https://www.fuse-t.org/)
- 对应的 SSHFS 分支：[macos-fuse-t/sshfs](https://github.com/macos-fuse-t/sshfs)；2026 年有文章推荐用 FUSE-T + SSHFS 在 Finder 里挂载。— [Andrew Zhu, Medium 2026](https://xhinker.medium.com/a-better-way-to-use-sshfs-in-macos-finder-in-2026-479b3b79bdf7)（只看到标题）

**rclone mount**
- macOS 上有三种挂载方式：macFUSE、FUSE-T、`rclone nfsmount`，**推荐 `rclone nfsmount`**（它自己启动 NFS 服务并完成挂载）；保持 Unicode 规范化的默认设置（macOS 偏好 NFD）。— [rclone mount docs](https://rclone.org/commands/rclone_mount/)
- FUSE-T 的坑：访问时间和修改时间无法分别设置，Finder 等工具查看文件时可能更新 mtime，导致 rclone 重新上传整个文件；`--read-only` 下写入会静默失败（截至 FUSE-T 1.0.14）；nfsmount 如果不指定 `--vfs-cache-mode`，挂载点是只读的，建议用 `writes` 或 `full`。— [rclone mount docs](https://rclone.org/commands/rclone_mount/)

**git 在网络挂载上的限制**
- git 的 fsmonitor 守护进程默认拒绝在网络挂载的仓库上工作；设置 `fsmonitor.allowRemote=true` 可以强开，但"属于实验性用法"；macOS/Linux 上 fsmonitor 用 Unix domain socket 做 IPC，而网络文件系统不支持这种 socket；`.git` 在网络盘上时 socket 会改建到 `$HOME/.git-fsmonitor-*`，如果 `$HOME` 也在网络盘上，则需要设置 `fsmonitor.socketDir`。— [git-fsmonitor--daemon docs](https://git-scm.com/docs/git-fsmonitor--daemon)

### Inferences
- **挂载的用途**：把 host 的 `~/Exchange` 或产物目录经 SMB 挂到 laptop，用 Finder 或 Quick Look 看日志和截图；**不要**把 host 的仓库挂到 laptop 上再在 laptop 上跑 `git status`、`npm install` 或编辑器索引。正确做法是 SSH 进 host 执行命令，或用 Mutagen/Syncthing 在本地保留副本。
- 远程时 SMB 挂载地址用 `smb://<host 的 MagicDNS 名>` 或 `smb://100.x.y.z`；SMB 445 端口只在 tailnet 内可达，不要暴露到公网。建议开启 "Only allow SMB encrypted connections"（Tailscale 已经加密一层，但 LAN 直连时仍然有意义）。
- Spotlight 与网络卷：一般经验是 SMB 挂载默认不被本地 Spotlight 索引。但 host 本机的 Spotlight 会索引 host 上的 node_modules 和 agent worktree，可以把这些目录加入 Spotlight Privacy 排除，或放 `.metadata_never_index` 文件（一般经验，本轮未找到官方引用）。
- 在 macOS 26 上，FUSE-T（NFS/SMB 后端）风险最低，不需要 kext，也不需要降低安全等级。macFUSE 的 FSKit 后端在 26.x 上有未解决的 issue；kext 后端在 Apple silicon 上需要进 Recovery 降低安全等级（这是一般常识，本轮未从官方页面核对）。
- NFS：macOS 仍自带 nfsd，可以通过 `/etc/exports` 导出，但本轮没有找到 macOS 26 下的可引用资料，列入 Gaps。

## Q5. 一次性搬运：scp / rsync（openrsync 坑）与 herdr-paste-image 式"剪贴板 → 文件 → 路径"

### Takeaway
一次性传文件最可靠的是 `scp` 或 `rsync -e ssh`（走 SSH over Tailscale）。macOS Sequoia（15.x，约 2025 年春的更新）起系统自带的 `rsync` 被 openrsync 取代，只支持部分参数，xattr 相关参数有坑，建议两端都用 Homebrew 的 rsync 3.x。herdr-paste-image 插件只在本地把剪贴板图片存成 `~/.cache/...png` 并把路径打进 pane，**它不会把图片传到远端**，所以在 laptop 连 host 的远程 pane 场景下，贴进去的是 laptop 上的路径，host 上的 agent 读不到。

### Cited Findings
- macOS Sequoia 起，Apple 用 openrsync（ISC 许可）取代了 rsync 2.6.9；openrsync 只接受 rsync 参数的一个子集；执行 `rsync` 时，一个包装器会根据参数分派到 `/usr/libexec/rsync/rsync.samba` 或 `rsync.openrsync`。— [Der Flounder 2025-04-06](https://derflounder.wordpress.com/2025/04/06/rsync-replaced-with-openrsync-on-macos-sequoia/)；[Michael Tsai: Sequoia's New rsync](https://mjtsai.com/blog/2025/06/06/sequoias-new-rsync/)
- 扩展属性参数：`-E` 以前是 xattr 参数，行为有变化；有报告称使用 `--extended-attributes` 会导致崩溃。— 搜索摘要，来源 [AppleInsider](https://appleinsider.com/inside/macos-sequoia/tips/what-you-should-know-about-apples-switch-from-rsync-to-openrsync)；另有 Apple 社区的"rsync stalls in macOS 15"帖子。— [Apple Community 256010540](https://discussions.apple.com/thread/256010540)
- herdr-paste-image 的机制：用 `pngpaste`/`osascript`（macOS）、`wl-paste`、`xclip`、PowerShell（WSL）读剪贴板图片 → 存到 `~/.cache/herdr-paste-image/image_<timestamp>.png` → 用 `herdr pane send-text` 把路径打进当前 pane（不按回车）；如果复制的本来就是图片文件，就直接贴原路径；要求 herdr ≥ 0.7.0；绑定示例 `key = "prefix+i"`，`command = "herdr-paste-image.paste"`；环境变量 `HERDR_PASTE_IMAGE_DIR`、`HERDR_PASTE_IMAGE_KEEP_DAYS`（默认 14 天）、`HERDR_PASTE_IMAGE_QUIET`；README 明确是本地行为，没有远程上传功能，主要在 WSL2 上测试。— [ddfonseca/herdr-paste-image](https://github.com/ddfonseca/herdr-paste-image)
- 本地手册已记录："远程 pane（`--remote` / `machine add`）剪贴板在 laptop、进程在远端，曾有静默失败的问题"，并建议用 herdr-paste-image 或手动 `scp` 后贴路径；"herdr 远程贴图：相关 issue 已关闭，但修复版本未确认"。— 本地文档 [herdr 完整实施手册](../../../agents/herdr/herdr-完整实施手册-最终版.md)（§3.1.6、附录 C 第 5 条）

### Inferences
- **修补方案（推荐自己写一个小脚本，以 herdr-paste-image 的思路为基础）**：laptop 上 `pngpaste /tmp/x.png`（`brew install pngpaste`）→ `scp /tmp/x.png host:~/Exchange/shots/$(date +%s).png`（或 `tailscale file cp`）→ 把 **host 上的路径**打进 pane。可以 fork herdr-paste-image，在 "save" 和 "send-text" 之间插入一步 `scp`，并把路径改写成 host 路径。插件的 action 是在 herdr 客户端所在机器执行还是在 server 所在机器执行，决定了它读的是哪台机器的剪贴板，需要实测（见 Gaps）。
- 截图自动流转：把 laptop 的截图保存位置改到同步目录（`defaults write com.apple.screencapture location ~/Exchange/shots`），配合 Syncthing 单向同步到 host，大约 10 秒后 host 上就有该文件，agent 用固定路径读取。
- Homebrew 的 rsync 3.x（`brew install rsync`）在两端都装，并在 `rsync --rsync-path=/opt/homebrew/bin/rsync` 中显式指定，可以避开 openrsync 的参数子集问题。

### Gaps
- herdr 插件 action 在 `herdr --remote` 下到底在哪台机器执行：herdr 文档和插件 README 都没有说明。
- herdr 当前版本是否已原生修复远程 pane 贴图：本地手册说 issue 已关闭，但修复版本未确认；本轮没有找到对应的 changelog 条目。

## Q6. 跨机剪贴板：OSC 52、pbcopy/pbpaste over SSH、Deskflow、第三方同步

### Takeaway
在"laptop 终端 → SSH/herdr → host"这条链上，**OSC 52 是 host → laptop 复制文本的正路**（Ghostty、kitty、WezTerm 支持，iTerm2 需要勾选设置；经过 herdr 时有约 196 KB 的静默上限；图片基本不支持）。laptop → host 的文本直接粘贴进终端即可；图片走文件通道。`pbcopy`/`pbpaste` 在 SSH 会话里操作的是 **host 自己的**剪贴板，并且受 launchd 会话域影响，可靠性存疑。不依赖 Apple Account 的跨网络剪贴板同步可以用 ClipCascade、UniClipboard、Telltail 等在 tailnet 上跑。

### Cited Findings
**OSC 52 与终端**
- Ghostty 通过 `clipboard-read` 和 `clipboard-write` 两个选项控制 OSC 52，可设为 `allow`（另有 `ask`）；配合 tmux 使用时需要 `set -g allow-passthrough on`；OSC 52 查询 `?` 会让终端回传剪贴板内容，远程开启 read 有凭据外泄的风险。— 搜索摘要，来源 [Ghostty docs: OSC 52](https://ghostty.org/docs/vt/osc/52)（原文抓取超时）
- Ghostty 有一个讨论帖请求"支持 OSC 52 读取图片数据（binary/base64）"，说明目前 OSC 52 在 Ghostty 中是文本通道。— [ghostty discussion #10099](https://github.com/ghostty-org/ghostty/discussions/10099)（只看到标题）
- 终端支持矩阵：WezTerm 始终支持；iTerm2 需要勾选设置；kitty 支持且可配置。— [tmuxai terminal compatibility](https://tmuxai.dev/terminal-compatibility/)
- iTerm2 的设置项是 "Applications in terminal may access clipboard"，开启后终端内程序可以通过转义序列设置系统剪贴板。— [iTerm2 documentation](https://iterm2.com/documentation-one-page.html)
- kitty 默认在程序读取剪贴板时询问用户，由 `clipboard_control` 控制；kitty 另有"复制所有数据类型到剪贴板"的扩展协议。— [kitty clipboard kitten](https://sw.kovidgoyal.net/kitty/kittens/clipboard/)；[kitty: Copying all data types](https://sw.kovidgoyal.net/kitty/clipboard/)
- tmux：`set-clipboard` 需要设为 `on` 或 `external`（默认 `external`），terminfo 里需要有 `Ms` 能力，终端本身也要启用该功能；tmux 3.3+ 需要 `allow-passthrough on`。— 搜索摘要，来源 [tmux wiki: Clipboard](https://github.com/tmux/tmux/wiki/Clipboard)（原文抓取失败）
- herdr：`advanced.osc52_paste` 是可选的 OSC 52 粘贴支持，用来应答 `OSC 52 ; c ; ?` 读取查询，**默认关闭**；另有 `[ui.toast.clipboard] enabled` 用于复制成功的提示。— 搜索摘要，来源 [herdr CHANGELOG](https://github.com/ogulcancelik/herdr/blob/master/CHANGELOG.md) / [herdr config docs](https://herdr.dev/docs/configuration/)
- herdr：pane 内程序写入超过约 196 KB 的 OSC 52 内容时，**静默丢弃**，没有 toast、警告或日志；在 macOS 27.0 上的 Ghostty 和 Android Termux 上复现；直接发给外层终端或走普通 SSH 则正常；issue 以 "not planned" 关闭。— [herdrdev/herdr #4194](https://github.com/herdrdev/herdr/issues/4194)
- herdr 远程模式下，主题、侧边栏布局和复制行为都来自**客户端**本地配置。— [herdr config docs](https://herdr.dev/docs/configuration/)

**pbcopy / pbpaste over SSH**
- 原理：macOS 的剪贴板（pasteboard）服务注册在"每用户"的 bootstrap namespace 中，只有该 namespace 里的进程能访问；tmux 调用 `daemon(3)` 后会落到根 namespace 而失去剪贴板访问；tmux 2.6（2017-09）已内置 reattach-to-user-namespace 的功能。— [ChrisJohnsen/tmux-MacOSX-pasteboard](https://github.com/ChrisJohnsen/tmux-MacOSX-pasteboard)
- GUI 终端和 SSH 会话的分界在 launchd 域：Aqua（`gui/<uid>`）对 Background（`user/<uid>`）；钥匙串解锁、TCC、pbcopy、TouchID、osascript、通知等行为都因此不同（可以用 `launchctl managername` 查看）。— 搜索摘要，来源 [the KodeLab: macOS GUI Terminal vs SSH Sessions](https://thekodelab.com/en/posts/macos-gui-terminal-vs-ssh-session/)（原文抓取为空）
- Mac 对 Mac 经 SSH 运行 TUI（opencode 1.2.24，远端 macOS 26.3.1）时，TUI 提示"已复制"，但远端 `pbpaste` 显示的仍是旧内容，issue 以 "not planned" 关闭。— [anomalyco/opencode #16962](https://github.com/anomalyco/opencode/issues/16962)
- 经典变通方案（2010）：laptop 上用 launchd 监听 127.0.0.1:2224 并交给 `/usr/bin/pbcopy`；`~/.ssh/config` 加 `RemoteForward 2224 127.0.0.1:2224`；远端用 `cat | nc -q1 localhost 2224` 代替 pbcopy；作者提醒这个端口除了 SSH 本身没有额外鉴权。— [Sean Coates: Remote pbcopy](https://seancoates.com/blogs/remote-pbcopy)
- 2026 年仍有文章讲"把远程命令输出复制到 macOS 剪贴板"（OSC 52 + 脚本）。— [IT Notes 2026-05-26](https://it-notes.dragas.net/2026/05/26/copying-remote-command-output-to-your-macos-clipboard/)；工具 [Meteors27/remote-pbcopy](https://github.com/Meteors27/remote-pbcopy)（OSC 52 实现）

**软件 KVM 与第三方同步**
- Deskflow（开源软件 KVM）支持剪贴板共享，但 2026 年有多个 issue：macOS 截图（图片）粘贴到 Windows 11 失败或变成全黑，只有文本正常；另有"单向粘贴失败"的 issue；讨论帖在问"是否支持剪贴板图片"。— [deskflow #9790](https://github.com/deskflow/deskflow/issues/9790)；[deskflow #9781](https://github.com/deskflow/deskflow/issues/9781)；[deskflow discussion #9395](https://github.com/deskflow/deskflow/discussions/9395)
- ClipCascade：开源，自动同步剪贴板，端到端加密，支持文本、图片、文件；默认模式是 P2S（经服务器中转，可以自建），也可以开 P2P 模式；支持 Windows、macOS、Linux、Android。— [Sathvik-Rao/ClipCascade](https://github.com/Sathvik-Rao/ClipCascade)；[XDA 介绍](https://www.xda-developers.com/open-source-self-hosted-app-syncs-clipboard-across-devices/)
- UniClipboard：本地优先、点对点、端到端加密，不需要账号或中心服务器；可以在 LAN 上工作，也可以经服务器节点或 Tailscale。— [uniclipboard/uniclipboard](https://github.com/uniclipboard/uniclipboard)
- Telltail：Go 应用，让 tailnet 内的机器共享剪贴板（文本复制和粘贴）。— [Tailscale 博客访谈：Telltail](https://github.com/tailscale-dev/tailscale-dev/blob/main/data/blog/telltail-universal-clipboard-ajit-singh-interview.mdx)

### Inferences
- **按方向选工具**：
  - host → laptop 文本：OSC 52（Ghostty 设 `clipboard-write = allow`，`clipboard-read` 保持 `ask` 或 `deny`）；大于约 196 KB 的输出（整段对话记录、长日志）不要走 OSC 52，改用 `ssh host cat file | pbcopy` 或文件通道。
  - laptop → host 文本：直接在终端里 ⌘V（bracketed paste），不需要额外工具。
  - laptop → host 图片：只能走文件（scp、Taildrop、同步目录），再贴路径（见 Q5）。
  - host → laptop 图片：`ssh host 'cat ~/path.png' > x.png`，或同步目录；OSC 52 不适用。
- `ssh host pbpaste | pbcopy`（从 laptop 的 GUI 终端执行）：管道右侧的 `pbcopy` 在 laptop 本地的 Aqua 会话里执行，没问题；左侧 `pbpaste` 在 host 的 SSH 会话里执行，能否读到 host 的剪贴板取决于 host 上是否有同一用户的 GUI 登录，以及 launchd 域。现有资料互相矛盾，**需要在 host 上实测**：`ssh host 'launchctl managername; pbpaste | wc -c'`。在无头的 host 上（无人登录 GUI），预计会失败。
- 安全：OSC 52 **读取**（`clipboard-read = allow`，或 herdr 的 `osc52_paste = true`）意味着远端任何程序（包括被 prompt 注入的 agent）都能读走 laptop 剪贴板里的密码或令牌。对跑着多个 AI agent 的 host，应保持 read 为 `ask` 或 `deny`，只放开 write。
- 第三方剪贴板同步工具（ClipCascade、UniClipboard）会把**所有**复制内容（包括密码）实时推到另一台机器；在 agent 主机上安装应谨慎，至少启用端到端加密，并把服务绑定在 tailnet 内。
- Deskflow 在"我坐在 laptop 前、不操作 host 键鼠"的远程场景里用处不大（它的主要用途是在同一张桌上共享键鼠）；远程时只有剪贴板部分有意义，且对图片支持不稳定。

### Gaps
- Ghostty `clipboard-read` / `clipboard-write` 的确切默认值（一般认为 read=ask、write=allow），因原文抓取超时未能核对。
- macOS 26 上 SSH 会话中 `pbpaste` 在有、无 GUI 登录两种情况下的实际行为：没有找到权威说明。尝试在本机 `ssh localhost` 实测，因为没有配置公钥认证而失败（测试时写入的 known_hosts 条目已用 `ssh-keygen -R localhost` 移除，会留下 known_hosts.old 备份）。
- Paste（iCloud 同步）、Maccy 等剪贴板管理器的跨机能力：本轮未检索；Maccy 通常被认为只在本地工作，未核对。
- KDE Connect 的 macOS 版本在 2026 年的状态：未检索到。

## Q7. 通知：把 host 的通知送到 laptop

### Takeaway
坐在 laptop 前时，首选 herdr 客户端的 `ui.toast`：laptop 用 `herdr --remote` 或 `machine add` 接入 host，`delivery = "system"` 或 `"terminal"`，这样 host 上 agent 的状态变化在 laptop 上弹出。离开电脑或需要推到手机时用 ntfy（可以自建在 tailnet 内）。在 host 上通过 SSH 调用 `terminal-notifier` 不可靠：它是 2017 年基于已弃用 API 的二进制，在 macOS 26 上不带 `-sender` 参数会静默丢弃通知，而且通知会弹在 host 上，不会弹在 laptop 上。

### Cited Findings
- herdr `ui.toast.delivery` 可选：`"herdr"`（应用内 toast）、`"terminal"`（外层终端通知，**SSH 下可用**）、`"system"`（本机系统通知服务）、`"off"`；herdr 不会为当前活跃 tab 弹 toast。— [herdr config docs](https://herdr.dev/docs/configuration/)
- 本地手册的做法："laptop 系统通知：客户端配置 `delivery = "system"`；通过 `machine add` 接入的宿主 agent 一并提醒"；通知出口还有 ntfy / moshi-hook；ntfy 由 Claude Code hook（`~/.claude/hooks/ntfy-notify.sh`）触发。— 本地文档 [herdr 完整实施手册](../../../agents/herdr/herdr-完整实施手册-最终版.md)（§2.3、§3.6.2、§3.10、§5.9.1）
- terminal-notifier：在 macOS 26 上，不提供 `-sender` 参数时通知会被静默丢弃（Apprise 的 `macosx://` 通知因此失效）。— [caronc/apprise #1705](https://github.com/caronc/apprise/issues/1705)
- terminal-notifier 2.0.0 是 2017 年基于 NSUserNotification（10.14 起弃用）的二进制；`-sender` 会按进程真实的 bundle 身份校验，冒充 iTerm 的通知会被丢弃；替代品是 `alerter`（用 Swift 基于 UNUserNotificationCenter 重写）。— 搜索摘要，来源可能是 [Viktor Gamov: Thirty lines to make Claude Code feel native in tmux and iTerm2](https://gamov.io/posts/tmux-iterm2-claude-code/)（未打开原文核对归属）
- ntfy 官方的桌面端方案是 PWA（浏览器安装的 Web App）。— [ntfy docs: From the Desktop](https://docs.ntfy.sh/subscribe/pwa/)；另有 CLI 订阅。— [ntfy docs: CLI](https://docs.ntfy.sh/subscribe/cli/)
- 第三方原生 macOS ntfy 客户端：`ntfy-macos`（原生，支持 SF Symbols、图片、按钮，可在收到消息时触发 shell 脚本）、`ntfy-mac`（后台守护进程，转发到通知中心，支持自动发现已订阅的 topic）、`ntfy-app`、`ntfy-desktop`。— [laurentftech/ntfy-macos](https://github.com/laurentftech/ntfy-macos)；[jkrumm/ntfy-mac](https://github.com/jkrumm/ntfy-mac)；[rubix-studios-pty-ltd/ntfy-app](https://github.com/rubix-studios-pty-ltd/ntfy-app)；[Aetherinox/ntfy-desktop](https://github.com/Aetherinox/ntfy-desktop)
- SSH 会话处于 Background launchd 域，osascript 和通知等 GUI 服务的行为与 GUI 终端不同。— 搜索摘要，来源 [the KodeLab](https://thekodelab.com/en/posts/macos-gui-terminal-vs-ssh-session/)
- "Over SSH 也能收到 macOS 通知"的做法（把终端通知转发回本地）有现成文章和项目。— [DEV: macOS notifications even over SSH](https://dev.to/jfpio/how-to-get-macos-notifications-for-long-running-processes-even-over-ssh-154d)；[ariccb/terminal-notifier-for-macos](https://github.com/ariccb/terminal-notifier-for-macos)（只看到标题和摘要）

### Inferences
- **三层通知**：
  - ① 在 laptop 前：herdr 客户端 toast，`delivery = "system"`，由 laptop 本机弹出，不依赖 host 的 GUI 会话；
  - ② 通用的终端层：host 上的 hook 输出 OSC 9 或 OSC 777 转义序列，经 SSH 传到 laptop 上的 Ghostty/iTerm2，由它们弹出（herdr `terminal` 模式就是这个思路；OSC 9/777 的具体支持情况本轮未逐一核对）；
  - ③ 离开电脑时：ntfy。服务端可以自建在 host 或 tailnet 内的另一台机器上，只监听 Tailscale IP，这样 topic 不暴露到公网；laptop 用 ntfy-mac 等原生客户端订阅，手机用 ntfy app。
- 不要在 host 上用 `terminal-notifier` 或 `osascript display notification`：这些通知弹在 host 的屏幕上，SSH 会话里还可能根本不生效。
- Pushover 等收费推送服务可作为 ntfy 的替代，本轮未检索细节。

### Gaps
- herdr `delivery = "terminal"` 具体使用哪种转义序列（OSC 9 / OSC 777 / OSC 99），以及 Ghostty 在 macOS 26/27 下点击通知能否聚焦回对应 pane：文档未说明（本地手册提到 Ghostty 支持"通知聚焦"，没有给出外部来源）。
- Pushover、Tailscale webhook 等其他通道：本轮未检索。
- `alerter` 在 macOS 26 下的维护状态：未核对。

## Q8. 横向的 macOS 陷阱（TCC / Spotlight / APFS 大小写 / 文件监听 / xattr）与推荐组合

### Takeaway
macOS 特有的坑集中在：launchd 会话域（SSH 会话与 GUI 会话中的剪贴板、通知、钥匙串、TCC 行为不同）、网络卷上的文件监听和 git fsmonitor 失效、默认不区分大小写的 APFS、openrsync 与 xattr、.DS_Store 以及 Spotlight 索引 node_modules。推荐组合是"git 为真相 + Syncthing 交换目录 + scp/Taildrop 一次性传输 + OSC 52 复制文本 + herdr toast 与 ntfy 通知"。

### Cited Findings
- launchd 域（Aqua `gui/<uid>` 与 Background `user/<uid>`）决定钥匙串、TCC、pbcopy、TouchID、osascript、通知等行为。— 搜索摘要，来源 [the KodeLab](https://thekodelab.com/en/posts/macos-gui-terminal-vs-ssh-session/)
- 剪贴板服务只对每用户 bootstrap namespace 可见。— [tmux-MacOSX-pasteboard](https://github.com/ChrisJohnsen/tmux-MacOSX-pasteboard)
- git fsmonitor 不支持网络文件系统（依赖 Unix socket），`allowRemote` 属于实验性。— [git-fsmonitor--daemon](https://git-scm.com/docs/git-fsmonitor--daemon)
- Syncthing 在不区分大小写的 macOS 上会报 case conflict；监听有 10 秒聚合延迟。— [Syncthing syncing.rst](https://raw.githubusercontent.com/syncthing/docs/main/users/syncing.rst)
- Mutagen 在 macOS 上用原生递归监听，Linux 上 node_modules 会耗尽 watch 配额。— [Mutagen watching](https://mutagen.io/documentation/synchronization/watching)
- openrsync 只支持部分参数，xattr 参数有坑。— [Der Flounder](https://derflounder.wordpress.com/2025/04/06/rsync-replaced-with-openrsync-on-macos-sequoia/)
- rclone 在 macOS 上要保持 Unicode 规范化默认值（NFD 问题）。— [rclone mount](https://rclone.org/commands/rclone_mount/)
- iCloud "Optimize Mac Storage" 会把 `.git` 驱逐成占位符。— [DEV Community](https://dev.to/ombak/many-mac-developers-misunderstand-does-icloud-secretly-ignore-git-files-the-reality-is-much-3970)
- .DS_Store 拖慢 SMB，可以用 `DSDontWriteNetworkStores` 关闭。— 搜索摘要，来源 [Cornell IT](https://it.cornell.edu/shared-file/apple-macos-and-cifs-performance-troubleshooting-tips)

### Inferences
- **推荐落地方案（按本场景）**：
  1. **代码**：只在 host 上保留工作树（agent 在 host 本地 APFS 上跑，git fsmonitor、FSEvents 正常）。laptop 通过 SSH 或 herdr 查看，需要本地 IDE 时用 `git worktree` + push/pull；或用 Mutagen `two-way-resolved --ignore-vcs -i node_modules -i dist` 做单编辑者同步（先确认 v0.18.1 在 26/27 上可用）。
  2. **交换目录**：两边各建 `~/Exchange/{shots,specs,logs,artifacts}`，由 Syncthing v2 同步（LAN 直连，远程时经 Tailscale IP，在 Syncthing 设备地址里填 `tcp://100.x.y.z:22000` 可以不依赖公共中继）；`.stignore` 排除 `node_modules`、`.DS_Store`、`*.tmp`。
  3. **一次性传输**：`scp` / Homebrew 的 rsync 3.x；或 Taildrop（前提是 host 不打 tag）。
  4. **Finder 浏览**：SMB（File Sharing，仅加密连接，只共享 `~/Exchange` 和产物目录，不共享整个家目录），或 Taildrive（alpha）。
  5. **剪贴板**：文本 host→laptop 用 OSC 52（经过 herdr 时 ≤196 KB）；laptop→host 用终端粘贴；图片一律走"文件 + 路径"（改造 herdr-paste-image，加一步 scp）；两台机器在同一房间时可以额外依赖 Universal Clipboard。
  6. **通知**：herdr 客户端 `ui.toast.delivery = "system"`；ntfy 自建在 tailnet 内作为离开电脑时的兜底；弃用 terminal-notifier。
- **TCC**：Syncthing、Mutagen agent、sshd 会话里的进程访问 ~/Desktop、~/Documents、~/Downloads 可能被 TCC 拦截或静默失败。把交换目录放在 `~/Exchange` 这类非受保护目录可以绕开大部分 TCC 弹窗；Taildrop 在 macOS 上落在 ~/Downloads（受保护目录），由 agent 读取时可能需要额外授权。这一点来自对 TCC 的一般了解，本轮未找到 macOS 26 专属的官方说明。
- **Spotlight**：host 上的 agent worktree、node_modules、Syncthing 目录都会被 Spotlight 索引，增加 IO；建议在 System Settings > Spotlight 中排除，或放置 `.metadata_never_index`（一般经验，未引用官方文档）。
- **xattr 与隔离属性**：通过 AirDrop、浏览器、Taildrop 收到的可执行文件可能带有 `com.apple.quarantine`，agent 执行这类构建产物前可能需要 `xattr -d com.apple.quarantine`。Taildrop 是否打这个标记，本轮未核对。

### Gaps
- macOS 26 下 SSH 会话、Syncthing、Mutagen agent 的 TCC 行为：没有找到官方或权威第三方的系统性资料。
- 2025–2026 年"两台 Mac 协同开发"的完整实践博客：本轮检索没有找到高质量的一手文章，现有资料多为单点工具文章。
