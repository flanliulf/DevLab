## 1. Apple Universal Control（通用控制）：要求、headless 主机、跨网络/Tailscale、剪贴板与拖放、macOS 26/27 可靠性

### Takeaway
Universal Control 零安装、自带跨设备拖放和复制粘贴，同桌场景下体验最好，但它**靠蓝牙 + Wi-Fi 近场（10 m 内）工作，底层是 AWDL 点对点 Wi-Fi，不走 IP 路由**，所以**不能跨网络，也不能走 Tailscale / VPN**。另外它只是把指针"推"到另一台 Mac 的**物理屏幕**上，所以 host 必须在同一张桌上接着显示器才有意义。

### Cited Findings
**官方要求（Apple 支持文档 102459）【已核实】** — [Apple Support: Universal Control](https://support.apple.com/en-us/102459)
- 系统：Mac 需要 **macOS Monterey 12.4 或更高**；iPad 需要 iPadOS 15.4 或更高。
- 支持的 Mac："All other Mac models introduced in 2016 or later, excluding MacBook Air (13-inch, 2017)"，另外包括 2017 年及以后的 iMac / iMac Pro 和 iMac (Retina 5K, 27-inch, Late 2015)。所有 Apple silicon Mac 都在范围内。
- 账号："Each device must be signed in with the same Apple Account using two-factor authentication"（同一个 Apple 账户 + 双重认证）。
- 无线：**Bluetooth、Wi-Fi、Handoff 都要打开**；设备之间 "Within 10 meters (30 feet)"。
- 数量：1 台主 Mac + 最多 2 台其他 Mac 或 iPad。
- 限制："your Mac must not be sharing its internet connection"（Mac 不能开"互联网共享"）；iPad 不能开蜂窝热点。
- 功能：支持跨设备**拖放**，支持 Command-C / Command-V 跨设备复制粘贴。
- 排障建议：首次设置时设备最好 "ideally within 1 meter (3 feet)"；检查 **VPN / 安全软件**；确认防火墙没有阻止传入连接。

**传输原理：AWDL 点对点 Wi-Fi**
- AWDL（Apple Wireless Direct Link）是 AirDrop、AirPlay、Handoff、Sidecar 和 Universal Control 共用的无线链路 — [CyberHoot: AWDL](https://cyberhoot.com/cybrary/apple-wireless-direct-link-awdl/)【搜索摘要】；[The Apple Wiki: AWDL](https://theapplewiki.com/wiki/Apple_Wireless_Direct_Link)【搜索摘要】
- 流程是先用 BLE 发现设备，再建立临时的点对点 Wi-Fi 连接，认证时用到 iCloud 凭据；无线网卡在信道之间"跳"，所以能一边连着 AP，一边和附近设备通信 — 搜索结果摘要（出处混在 [arXiv 2502.04538](https://arxiv.org/pdf/2502.04538) 等结果里，未逐字核对）【搜索摘要】
- "nearby devices that are connected to different infrastructure Wi-Fi networks can still communicate with each other using AWDL"。AWDL 是点对点而不是 mesh，包不经过中心节点或其他节点转发 — [Yggdrasil Network blog (2019)](https://yggdrasil-network.github.io/2019/08/19/awdl.html)【搜索摘要，资料较旧】

**macOS 26 Tahoe 上的可靠性**
- Apple Community 帖（2026-01-08）：2019 iMac（macOS Sequoia 15.7.3）和 MacBook Air M2（macOS Tahoe 26.2）之间，Universal Control 图标"出现约 1 秒后消失"，连接保持不住。重置蓝牙、重启、更新都没用。**解决办法：在 Tahoe 那台上退出 Apple 账户再登录，然后重启。** 其他建议：确认"放大时停用通用控制"已关闭（系统设置 › 辅助功能 › 缩放 › 高级）；在"显示器"设置里把通用控制关掉再打开 — [Apple Community thread 256222654](https://discussions.apple.com/thread/256222654)【已核实】
- 另有报告称 M1 MBP（Sequoia）和 M4 MBP（Tahoe）之间 UC 工作稳定，说明问题跟具体机器和配置有关，不是 Tahoe 普遍故障 — 同一次搜索的摘要，[Apple Community](https://discussions.apple.com/thread/256222654)【搜索摘要】
- macOS 27 Golden Gate：发布说明和评测摘要里没看到针对 Universal Control 的变化（Continuity 方面提到的是 Messages 同步修复和 Sidecar 触控）— [MacRumors 50 new features](https://www.macrumors.com/2026/09/17/new-features-changes-macos-27/)，[Six Colors review](https://sixcolors.com/post/2026/09/macos-27-golden-gate-review-bridging-the-tahoe-gap/)【搜索摘要，未逐条核对】

**headless Mac mini**
- M1 及以后的 Mac mini 不接显示器时会**自动创建虚拟显示器**，不需要 HDMI 假负载（dummy plug）。但默认虚拟分辨率很低（约 1280×1024 或更低），所以有人加 dummy plug 来提高分辨率、避免远程会话时窗口尺寸错乱 — [Astropad: Dummy plug for headless Mac mini](https://astropad.com/blog/dummy-plug-headless-mac-mini/)【搜索摘要】
- 有搜索摘要提到"需要先接显示器完成设置"，也有用户反映 headless mini 上 UC 用不好，建议 headless 场景改用屏幕共享 — [Apple Community headless mac mini M1](https://discussions.apple.com/thread/252079747)【搜索摘要，信号弱】
- Apple 官方文档没有提到 headless / 虚拟显示器下的 Universal Control — [Apple Support 102459](https://support.apple.com/en-us/102459)【已核实：文档中无相关表述】

### Inferences
- **跨网络 / Tailscale：不能用。**【推断，把握较高】UC 依赖 BLE 近场发现 + AWDL 点对点 Wi-Fi，不经过 IP 路由，Tailscale 的 100.x 虚拟网卡根本不在这条路径上。host 在别处时，无论怎么配 Tailscale 都用不了 UC。Apple 排障文档专门提到"检查 VPN"，说明 VPN 软件甚至可能干扰同桌时的 UC；如果装了 Tailscale 的同桌 Mac 之间 UC 不稳，可以先暂停 Tailscale 排除一下（这一点没找到专门的报告）。
- **反过来，同桌但不在同一个 Wi-Fi 网络下（例如笔记本连访客 Wi-Fi，host 走有线网）UC 很可能仍然能用**，因为 AWDL 不要求两台设备连同一个 AP。【推断，基于 AWDL 原理；Apple 文档只说要"打开 Wi-Fi"，没说要同一个网络】
- **host 只插网线、把 Wi-Fi 关掉 → UC 必然失败**，因为 Apple 要求 Wi-Fi 和蓝牙都打开。Mac mini / Studio 当 host 时要记得保持 Wi-Fi 无线电开启（不用连任何网络）。【推断，基于官方要求】
- **headless host 用 UC 没有实际意义**：UC 是把光标移到对方"显示器"边缘再进去。就算 headless mini 有虚拟显示器，甚至插了 dummy plug，你在笔记本上也**看不到** host 的画面，等于盲操作。要"看见并操作" headless host，应该用屏幕共享 / 远程桌面（见本系列 02 号笔记）。屏幕共享窗口本身就会转发键鼠，这时候再用 UC 就多余了。【推断】
- 拓扑：UC 允许 1 主 + 2 从，笔记本当主、host 当从正好。而且任何一台的键鼠都能发起控制，不像软件 KVM 那样固定 server/client。【官方数量限制已核实；"任一台都能发起"是常识性判断，未专门核对】
- 优点汇总：零安装、苹果签名、无需辅助功能授权、拖放文件和通用剪贴板开箱即用。缺点：不能跨网、偶发"握手成功又断开"、依赖 iCloud 账户状态（退出再登录往往能修好）。

### Gaps
- Universal Control 能否在**登录窗口 / FileVault 解锁前**使用：本次没找到权威说明（一般认为需要已登录的用户会话和 iCloud，但未核实）。
- Apple 没有公开 UC 的协议文档；"BLE + AWDL"的描述来自第三方资料和安全研究，不是 Apple 官方说法。
- 没找到 headless Mac mini + dummy plug + UC 的可靠实测报告。
- 没找到 Tailscale 与 UC 共存冲突的专门报告。
- 没找到 macOS 27 中 UC 是否有改动或回归的具体资料。

## 2. Sidecar 与"把 Mac 当显示器"的替代方案（AirPlay to Mac、Target Display Mode）

### Takeaway
Sidecar **只能把 iPad 当 Mac 的副屏**，不能把 Mac 当显示目标。"Mac 当显示器"目前唯一的原生路径是 **AirPlay 接收器（macOS Monterey+）**，但它只传画面、不回传输入，而且主要靠同一局域网或近场发现，替代不了远程桌面。Target Display Mode 只存在于 2009–2014 年的 iMac，Apple silicon 上已完全不适用。

### Cited Findings
- **Sidecar 要求【已核实】** — [Apple Support 102597: Sidecar](https://support.apple.com/en-us/102597)
  - macOS Catalina 10.15+，iPadOS 13+；Mac：MacBook Air 2018+、iMac Retina 5K 27" Late 2015、其他 2016+ 机型；iPad：所有 iPad Pro、iPad 6 代+、iPad mini 5 代+、iPad Air 3 代+。
  - 同一 Apple 账户 + 双重认证；无线使用时需在 10 m 内，并打开 Bluetooth、Wi-Fi、Handoff；有线（USB）时 iPad 要信任这台 Mac；Mac 不能开互联网共享。
  - 方向是单向的：iPad 作为 Mac 的第二显示器。文档里没有任何"Mac 作为显示目标"的说法。
- **macOS 27 的 Sidecar 变化**：Sidecar 从只支持 Apple Pencil 扩展到支持 iPad 触屏操作 — [MacRumors: new features macOS 27](https://www.macrumors.com/2026/09/17/new-features-changes-macos-27/)【搜索摘要，未打开原文核对】（与本场景无直接关系，只说明 Sidecar 仍然是 Mac→iPad 方向）
- **AirPlay to Mac（AirPlay 接收器）**
  - macOS Monterey 或更高的受支持 Mac 才有"AirPlay 接收器"选项；受支持机型包括 MacBook Pro 2018+、MacBook Air 2018+、iMac 2019+、iMac Pro 2017、**Mac mini 2020+**、Mac Pro 2019 — [Apple Mac User Guide: Set up your Mac to be an AirPlay receiver](https://support.apple.com/guide/mac-help/set-up-your-mac-to-be-an-airplay-receiver-mchleee00ec8/12.0/mac/12.0)【搜索摘要，引用 Apple 页面】
  - "允许 AirPlay 的对象"有三档：**当前用户**（只有登录同一 Apple ID 的设备）、**同一网络中的任何人**、**所有人**；旧设备在设为后两档时可以用较低分辨率 AirPlay — 同上【搜索摘要】
  - Mac→Mac 用 AirPlay 做镜像或扩展屏的步骤说明，只在第三方博客里找到 — [Pigeoncast: AirPlay Mac to Mac](https://pigeoncast.com/blogs/airplay-mac-to-mac)【搜索摘要，第三方来源，可信度一般】
- **Target Display Mode（目标显示器模式）**
  - Apple 文档：只有 2009/2010 年 24"/27" iMac（Mini DisplayPort）和 2011–mid 2014 iMac（Thunderbolt / Thunderbolt 2）支持，并且要运行 **macOS High Sierra 10.13.6 或更早** — [Apple Support 105126: Use iMac as a display with target display mode](https://support.apple.com/en-us/105126)【搜索摘要，引用 Apple 页面】
  - 所有 Retina iMac（从 Late 2014 5K iMac 起）都不支持，该功能事实上已停止 — [Apple Community: About Target display mode](https://discussions.apple.com/docs/DOC-250008142)【搜索摘要】

### Inferences
- 对"笔记本看 host 画面"这个需求：理论上可以让 host 通过 AirPlay 把画面镜像或扩展到笔记本（笔记本开启 AirPlay 接收器），但 **AirPlay 只传视频，不回传键鼠**。要从笔记本操作 host 仍然需要 UC 或软件 KVM，而 UC 本身又依赖 host 的"显示器"，链路很别扭，实用价值很低。正确的做法是屏幕共享 / 远程桌面，它同时传画面和输入（见 02 号笔记）。【推断】
- AirPlay 接收器的发现依赖 Bonjour（同一局域网）或 AWDL 近场。经过 Tailscale 能不能用，本次**未核实**；普遍认为 Tailscale 默认不转发 mDNS / Bonjour 广播，所以大概率不行。【推断，未核实】
- Sidecar 和 Target Display Mode 在本场景都可以直接排除。

### Gaps
- 没打开 Apple 官方"Mac 镜像 / 扩展到另一台 Mac（AirPlay）"的操作页核对原文（只拿到第三方博客的描述）。
- 没找到 AirPlay to Mac 的端到端延迟数据，也没找到经 Tailscale 使用的实测报告。

## 3. 软件 KVM 在 Apple silicon + macOS 26/27 上的现状（Deskflow / Input Leap / Barrier / Synergy 3 / ShareMouse / Mouse Without Borders / Lan Mouse）

### Takeaway
2026 年开源首选是 **Deskflow**：GPL-2.0，非常活跃，默认开 TLS 1.3，支持剪贴板，有原生 arm64 包，Synergy 官方赞助。但 **v1.26.0 在 macOS 27 上会崩溃**，要等基于 Qt 6.12 / 6.11.3 构建的 1.27.0。**Input Leap 已在 GitHub 归档**，Barrier 自 2021 年起停止发布，这两个都不建议新装。**Synergy 3** 是 Deskflow 的商业下游，一次性买断 $15–29，TLS 只在 Plus 及以上。**ShareMouse** 只支持 Mac 和 Windows，官方声明只能在局域网用。**Lan Mouse** 在 2026-06 的 v0.11.0 才加入 DTLS 加密，**目前不支持剪贴板**。这些工具都需要 macOS 的"辅助功能"授权，而且都只共享输入，不传画面。

### Cited Findings

## 4. 软件 KVM 能否跨 Tailscale / VPN / 不同网络使用？

### Takeaway
Deskflow、Barrier、Input Leap、Synergy 都是**基于 IP 的 TCP client/server**（Deskflow 默认 24800），Lan Mouse 是 UDP 4242，**只要两台机器互相能访问对方的 IP / 端口，技术上就能跑在 Tailscale 上**，体验主要取决于往返时延（RTT）。直连（非 DERP）、RTT 在 20 ms 以内时可以接受，走 DERP 中继会明显发粘。但**真正的限制在屏幕**：host 不在眼前时，你看不到它的画面，键鼠共享就没有意义。所以 Tailscale 在这一层只适合当"同桌但不在同一网段"时的备用链路。ShareMouse、Logitech Flow、Universal Control 都明确只支持局域网或近场。

### Cited Findings
- Deskflow 的连接是 IP/主机名 + TCP 端口（日志显示 `192.168.68.78:24800`，并先尝试了 `.local` 的 IPv6 link-local 地址）— [Deskflow #10020 日志](https://github.com/deskflow/deskflow/issues/10020)【已核实】
- Deskflow v1.26 起，client 的 server 地址可以填**多个主机名或 IP，依次尝试** — [v1.26.0 release notes](https://github.com/deskflow/deskflow/releases/tag/v1.26.0)【已核实】
- Deskflow 维护者在"通过代理跨 WAN 隧道连接"的 issue 下说，他们试验过一个中转 server/client 消息的代理工具，"It worked pretty well when hosted on a computer with relatively low ping (**<20 ms**)" — [Deskflow #7439 评论](https://github.com/deskflow/deskflow/issues/7439)【已核实：评论原文】
- Deskflow 仓库有 "Restrict deskflow client to using specific network" 的 issue（#9552，2026-03，已关闭），说明多网卡 / 多网络选择确实是真实需求 — [#9552](https://github.com/deskflow/deskflow/issues/9552)【只核实了标题】
- Tailscale：直连比中继吞吐更高、延迟更低；打洞失败时流量改走 DERP 中继，"additional latency" — [Tailscale Docs: Connection types](https://tailscale.com/docs/reference/connection-types)，[Poor performance between tailnet devices](https://tailscale.com/docs/reference/troubleshooting/poor-performance-tailnet)【搜索摘要】
- Lan Mouse 使用 UDP 4242 + DTLS，防火墙需放行这个 UDP 端口 — [Lan Mouse README](https://github.com/feschber/lan-mouse)【已核实】
- ShareMouse 官方说不能跨互联网、VPN 下不提供支持 — [ShareMouse FAQ](https://www.sharemouse.com/faq/)【已核实】
- Logitech Flow 要求"All computers must connect to the same wireless or wired network" — [Logitech Support: What is Logitech Flow](https://support.logi.com/hc/en-us/articles/1500005634742-What-is-Logitech-Flow-and-how-do-I-set-it-up-and-troubleshoot-it)【已核实】。同一子网内用 UDP 59867 广播发现；在路由器或防火墙后面时借助 Logitech 云服务发现（TCP 443 + UDP 59868）— [Flow network setup check for Mac](https://support.logi.com/hc/en-001/articles/360023196954-Flow-network-setup-check-for-Mac)【搜索摘要】
- Universal Control 只支持近场（10 m、BT + Wi-Fi）— [Apple Support 102459](https://support.apple.com/en-us/102459)【已核实】
- 没找到专门讲"Deskflow / Barrier over Tailscale"的社区帖或实测：两次针对性搜索（"Deskflow over Tailscale latency"、"Barrier Tailscale"）只返回了 Tailscale 通用性能文档和 Barrier 通用教程【如实记录：未找到】

### Inferences
- **可行性**：在两台 Mac 上都登录 Tailscale，client（host）的 server 地址填 `笔记本局域网 IP` 和 `笔记本 100.x IP / MagicDNS 名`（v1.26 支持多地址依次尝试），就能在"同桌但不在同一网段"（例如笔记本连访客 Wi-Fi、公司 VLAN 隔离、或开着公司全局 VPN）时继续用。【推断】
- **延迟与手感**：鼠标移动是高频小包，TCP 的队头阻塞在丢包时会造成卡顿。Tailscale 直连、同城 RTT 在 20 ms 以内基本可用（参考维护者的 <20 ms 说法）；走 DERP 或跨洲时会明显发粘。Lan Mouse 用 UDP，理论上更抗丢包，但没有剪贴板。【推断】
- **安全**：Deskflow TLS 1.3 加上 Tailscale WireGuard 相当于双层加密。可以用 Tailscale ACL 只放行笔记本到 host 的 TCP 24800，避免在公网或局域网暴露端口。【推断】
- **根本局限**：host 在远处时，软件 KVM 让你"摸得到但看不见"。远程场景应该用屏幕共享、Jump Desktop、Parsec 等（见 02 号笔记），它们自带输入转发。**所以本层（Universal Control / 软件 KVM）只适用于两台 Mac 同桌、host 显示器在眼前的情况。**【推断，与任务前提一致】
- 本机发现机制（Bonjour / `.local`、UDP 广播）通常不能穿过 Tailscale（Tailscale 默认不转发 mDNS 和广播），所以一定要**手动填 IP**；ShareMouse 要关掉 UDP 广播改填 IP。【推断，Tailscale 不转发 mDNS 这一点本次未核实】

### Gaps
- 没找到 Deskflow / Synergy / Lan Mouse 在 Tailscale 上的实测延迟数据或社区经验帖。
- 没核实 Tailscale 当前是否转发 mDNS / 广播（据了解默认不转发，但本次没有读到官方文档原文）。
- 没找到 Synergy 3 是否有云中继或跨网功能的官方说明（论坛只讨论了 VPN 问题）。

## 5. 硬件 KVM、USB 切换器与多设备键鼠（Logitech Flow / Easy-Switch、Magic Keyboard 配对限制）：什么时候硬件更好？

### Takeaway
硬件 KVM 或 USB 切换器能切换**外接**显示器和外接键鼠，零软件、零延迟，在登录窗口、FileVault 和 Secure Input 下也照常工作。但它**切不了笔记本自带的键盘和触控板**，也就不满足"用笔记本自己的键鼠控制 host"这个原始诉求。Mac 还有几个特殊点：不支持 DisplayPort MST；Touch ID 妙控键盘经过 KVM 的 HID 口会失效；Magic 系列配件一次只记一个蓝牙配对。Logitech Flow 是"软件 + 多通道硬件"的混合方案，要求同一网络，只支持复制粘贴，不支持拖放。

### Cited Findings
- **macOS 不支持 DisplayPort MST**：双屏需要每块屏各接一根线；KVM 最好带 **EDID 模拟**，避免切换时窗口和桌面图标被重新排列 — [TESmart: Facts before buying a KVM for MacBook](https://www.tesmart.com/blogs/news/facts-to-consider-before-buying-a-kvm-switch-for-your-macbook)【搜索摘要，厂商博客】
- 切换主机时偶尔识别不到显示器（EDID / 握手时序问题）；建议更新固件、用短的认证 TB4 线，必要时再切一次或给显示器 USB 链路断电重启 — 同一次搜索的摘要【搜索摘要，来源混合，可信度一般】
- **Touch ID 妙控键盘 + KVM**：用户实测 "Magic Keyboard with Touch ID and Numeric Keypad"（Apple silicon 款）接在 KVM 的 HID 口上 "fully does not work … Neither the keyboard, nor the touchid functions"；接在 USB 3 直通口上键盘能用，但 KVM 热键失效 — [Level1Techs forum](https://forum.level1techs.com/t/does-apple-keyboard-with-touchid-work-through-kvm-hid-port/249462)【已核实】
- **Magic Keyboard / Mouse / Trackpad 一次只存一个蓝牙配对**，连到新 Mac 会顶掉旧的配对；切换方法有三种：在"蓝牙"里忘记设备再重新配对、用 USB 线插一下自动配对（最快的原生方法）、第三方切换 App — [Switchy blog: Magic Keyboard on multiple devices (2026)](https://mangobuns.com/switchy/blog/magic-keyboard-multiple-devices/)【搜索摘要，第三方厂商博客】；用线缆连接即自动配对 — [Apple Support 119917](https://support.apple.com/en-ng/119917)【搜索摘要，Apple 页面】；第三方免费工具 Magic Switch — [joshua.hu: Magic Switch](https://joshua.hu/magic-switch-easily-switch-magic-keyboard-trackpad-mouse-between-mac-macbook-macos)【搜索摘要】
- **Logitech Flow**【已核实】— [Logitech Support: What is Logitech Flow](https://support.logi.com/hc/en-us/articles/1500005634742-What-is-Logitech-Flow-and-how-do-I-set-it-up-and-troubleshoot-it)
  - 所有电脑都要装 Logi Options+；需要兼容的 Logitech 鼠标，通过 Easy-Switch 通道（USB 接收器或蓝牙）配对 2–3 台电脑；所有电脑要连同一个有线或无线网络；兼容的 Logitech 键盘可以"跟随"鼠标切换
  - 光标移到屏幕边缘即可切换；可以跨机复制粘贴文本、图片、文件；**"Dragging files from one computer to drop on another is not supported"**
  - 电脑睡眠或停在**登录界面时不可用**；需要放行特定 TCP/UDP 端口；大文件传输可能要几分钟
  - macOS 上可能要授予蓝牙、输入监控、辅助功能等权限 — [Flow network setup check for Mac](https://support.logi.com/hc/en-001/articles/360023196954-Flow-network-setup-check-for-Mac)【搜索摘要】

### Inferences
- **KVM 切不了笔记本内置输入设备**：本用户的诉求是"用笔记本自己的键盘和触控板控制 host"，硬件 KVM 做不到（内置键盘和触控板不经过 USB 口）。只有在"合盖笔记本 + 外接显示器 + 外接键鼠"的桌面模式下，KVM 才适用。【推断，把握高】
- **硬件 KVM 更好的情况**：(1) 桌上只有一块大显示器，要在笔记本和 host 之间切换**画面**，而软件方案都不传画面；(2) 要在 host 的登录窗口、FileVault 解锁、恢复模式或系统卡死时输入；(3) 不想给第三方软件辅助功能权限，或公司 MDM 禁止安装；(4) 对延迟零容忍（游戏、绘图）。【推断】
- **Mac 用 KVM 的注意事项**：选带 USB-C / Thunderbolt 和 EDID 模拟的型号；需要双屏时要双 DP/HDMI 通道（因为 Mac 不支持 MST）；**Touch ID 键盘要接 USB 直通口，或者干脆不经过 KVM**。Apple silicon 基础款芯片外接显示器数量有限，也会影响 KVM 双屏方案（本次未核实具体数量）。【推断】
- **性价比折中**：Logitech MX 系列键鼠的 Easy-Switch（按一下切通道）是"硬件级"的多机切换，不依赖网络。Flow 是在它之上的软件层，但 Flow 要求同一网络、不支持拖放、登录界面不可用，所以和 Universal Control 相比，Mac↔Mac 下没有明显优势。【推断】
- Magic Keyboard / Trackpad 在两台 Mac 之间切来切去很麻烦（一次只记一个配对）。如果想用一套外接 Magic 配件控制两台，**Universal Control 本身就是最好的"切换器"**：配件只配对笔记本，由 UC 转发给 host。【推断】

### Gaps
- 没有针对 2026 年具体 Mac 专用 KVM 型号（TESmart、CKL、Sabrent、UGREEN 等）的实测对比，也没有价格数据。
- Touch ID 键盘经 KVM 的 USB 直通口时，Touch ID 本身能否工作，没有找到明确结论（Touch ID 与单台 Mac 的安全隔区配对，推测切换后需要重新配对，未核实）。
- 没核实 Logitech Options+ 当前对 macOS 26/27 的支持状态。

## 6. 关键限制与适用边界：共享的是"输入"，不是"屏幕"

### Takeaway
本层所有方案（Universal Control、Deskflow/Synergy/ShareMouse/Lan Mouse、Logitech Flow、硬件 KVM 的键鼠部分）都**只传输入，不传画面**，Deskflow 自己的说法是 "software KVM (but without the video)"。所以本层**只适用于两台 Mac 在同一张桌上、host 接着自己的显示器并且在眼前**的情况。host 在远处（只能通过 Tailscale 访问）时，应该用屏幕共享 / 远程桌面（02 号笔记）加 herdr/SSH，本层不适用。

### Cited Findings
- Deskflow README："It's like a software KVM (**but without the video**)" — [deskflow/deskflow](https://github.com/deskflow/deskflow)【已核实】
- Universal Control 的交互方式是把指针移出一台设备的屏幕边缘，进入另一台设备的屏幕，要求设备在 10 m 以内 — [Apple Support 102459](https://support.apple.com/en-us/102459)【已核实】
- Logitech Flow 同样是 "move your cursor to the edge of the screen"，并要求同一网络 — [Logitech Support](https://support.logi.com/hc/en-us/articles/1500005634742-What-is-Logitech-Flow-and-how-do-I-set-it-up-and-troubleshoot-it)【已核实】
- headless Mac mini 的虚拟显示器默认分辨率低，远程会话时常加 dummy plug — [Astropad](https://astropad.com/blog/dummy-plug-headless-mac-mini/)【搜索摘要】
- host 显示器休眠时，Deskflow 把指针移进去不会唤醒显示器，要按一下键才行 — [Deskflow #10020](https://github.com/deskflow/deskflow/issues/10020)【已核实】

### Inferences
- **决策矩阵（本用户场景）**【推断】
  | 情况 | 推荐 | 理由 |
  |---|---|---|
  | 同桌，host 接显示器，两台都在 macOS 26 | **Universal Control** 为主 | 零安装、能拖放文件、有通用剪贴板；笔记本内置键盘和触控板直接可用 |
  | 同桌，UC 不稳定 / 想用热键切换 / 不在同一网段 | **Deskflow**（笔记本作 server，host 作 client；server 地址填 LAN IP + Tailscale IP） | TLS 1.3、剪贴板、免费；macOS 27 上要等 1.27 |
  | 同桌，只有一块显示器，笔记本合盖使用 | **硬件 KVM**（USB-C，带 EDID 模拟）或 UC + 两块屏 | 软件方案不能切换画面 |
  | host 在远处 | **屏幕共享 / 远程桌面 + herdr/SSH**（见 02 号笔记） | 本层所有方案都看不到 host 画面，不适用 |
- **host 端准备清单**：保持 Wi-Fi 和蓝牙打开（即使走有线网）；和笔记本登录同一 Apple 账户并开启双重认证；打开 Handoff；Mac 不要开"互联网共享"；如果用 Deskflow，给 `Deskflow` 和 `deskflow` 进程都授予辅助功能权限，升级后删掉旧条目再重新授权；关闭 host 的系统睡眠（跑 agent 本来就要），显示器休眠后需要按键唤醒；开了 FileVault 的话，重启后的首次解锁要靠物理键盘或屏幕共享完成。【推断，综合上文来源】
- **升级时机**：UC 在 Tahoe 上偶发连接不稳，退出再登录 Apple 账户通常能修好。Deskflow 1.26 在 macOS 27 上会崩溃。两台 Mac 不要贸然升到 27，至少等 Deskflow 1.27 发布。【推断】

### Gaps
- 没有 Universal Control 和 Deskflow 在同一硬件上的延迟或手感对比测量。
- 没核实 Universal Control 和 Deskflow 同时运行时是否冲突（例如两者都抢屏幕边缘）。
