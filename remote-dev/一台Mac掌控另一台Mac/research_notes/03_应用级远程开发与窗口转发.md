# 应用级 / 窗口级远程开发：从笔记本 Mac 操作宿主 Mac（Apple silicon, macOS 26，运行 herdr + 多个 AI 编码 Agent）

> 调研日期：2026-09-24。场景：笔记本（client）经 SSH（Tailscale 或同一 LAN）连到宿主 Mac（host），宿主上 herdr 管理 Claude Code / Codex 等 Agent；目标是用笔记本自己的屏幕、键盘、鼠标编辑和审阅宿主上的代码与 diff，不走整屏远程桌面。
> 约定：每条事实都在旁边附来源；"Inferences" 部分是基于来源的推断或常识，未逐条核实；"Gaps" 是没查到或不可靠的内容。旧信息会标注。

---

## Q1. VS Code Remote-SSH、Remote Tunnels，以及 Remote 扩展在 fork 里的许可问题

### Takeaway
VS Code Remote-SSH 官方支持 macOS 10.14+ 作为 SSH 宿主（需要开启"远程登录"）。VS Code Server 跑在宿主上，UI 留在笔记本；宿主上的 AI Agent 与 VS Code 看到的是同一份磁盘文件，文件监听和 git 都在宿主上执行，所以 Agent 的改动会自然出现在编辑器里。Remote Tunnels 通过 Microsoft dev tunnels 中继，连接不需要 SSH。两者的 Remote 扩展都是闭源的，许可只允许在官方 VS Code 中使用，Cursor、Windsurf、VSCodium、code-server 都只能自己重新实现或用开源替代品。

### Cited Findings
**架构 / 要求**
- 扩展会在远端安装 VS Code Server。大多数扩展在 SSH 宿主上运行，但"影响 UI 的扩展（主题、代码片段）装在本地"。连上后打开的终端"自动在远端宿主运行" — [VS Code Docs: Remote SSH](https://code.visualstudio.com/docs/remote/ssh)
- 支持的宿主包括 "macOS 10.14+ (Mojave) SSH hosts with Remote Login enabled"。最低 1 GB RAM，建议 "at least 2 GB RAM and a 2-core CPU"。不支持 Alpine / 非 glibc Linux 宿主，也不支持 Windows 上的 PuTTY — [VS Code Docs: Remote SSH](https://code.visualstudio.com/docs/remote/ssh)；[Marketplace: Remote - SSH](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-ssh)
- **PATH / 环境变量（macOS 宿主的关键点）**：远端扩展宿主和终端的环境"基于默认 shell 的配置脚本……server 会以 **interactive login shell** 的方式启动默认 shell 的一个实例"来解析环境。所以 `~/.zprofile` 或 `~/.zshrc` 里的 Homebrew PATH 会生效，与普通 `ssh host cmd`（非交互）不同 — [VS Code Docs: Remote Troubleshooting / Tips](https://code.visualstudio.com/docs/remote/troubleshooting)
- 远端终端可以用 `if [ "$VSCODE_INJECTION" = "1" ]; then export EDITOR="code --wait"; fi`，让 `git commit` 等命令在 VS Code 里打开编辑器 — [VS Code Docs: Remote Troubleshooting](https://code.visualstudio.com/docs/remote/troubleshooting)

**端口转发**
- 有两种方式：通过 Command Palette 或 Ports 视图做会话期临时转发；在 SSH config 里写 `LocalForward` 做永久转发。另有 `remote.restoreForwardedPorts` 用来记住转发过的端口 — [VS Code Docs: Remote SSH](https://code.visualstudio.com/docs/remote/ssh)
- 自动转发默认靠扫描远端正在运行的进程来发现端口，可以设 `"remote.autoForwardPortsSource": "output"` 改为扫描终端和调试输出，`hybrid` 同时用两者。从 output 自动转发的端口在进程结束后不会自动关闭 — [vscode-docs remote release notes v1.54](https://github.com/microsoft/vscode-docs/blob/main/remote-release-notes/v1_54.md)；[microsoft/vscode#200795](https://github.com/microsoft/vscode/issues/200795)
- 已知问题：自动转发超过 20 个端口时，会提示 "Over 20 ports have been automatically forwarded"，并把设置切到 `hybrid`，之后可能失效 — [vscode-remote-release#10926](https://github.com/microsoft/vscode-remote-release/issues/10926)。宿主上有多个 Agent 各自起 dev server 时，这种情况很容易出现。
- 端口可见性默认是 "Private"，可以改成 "Public"（走 dev tunnels 时）。集成浏览器可以"通过远程连接代理其网络流量" — [VS Code Docs: Port forwarding](https://code.visualstudio.com/docs/debugtest/port-forwarding)

**Remote Tunnels（不需要 SSH）**
- 数据经 "Microsoft dev tunnels" 中继。托管端和连接端"需要用同一个 GitHub 或 Microsoft 账号认证"。加密是 "AES 256 in CTR mode"，实现开源。"VS Code doesn't set up any network listeners"，所以不用改防火墙 — [VS Code Docs: Remote Tunnels](https://code.visualstudio.com/docs/remote/tunnels)
- 每个账号最多注册 10 条 tunnel，超过时 CLI 会随机删掉一条未使用的。有防滥用的带宽限制。`code tunnel service install` / `uninstall` 可以把它装成后台服务 — [VS Code Docs: Remote Tunnels](https://code.visualstudio.com/docs/remote/tunnels)

**许可 / fork**
- Marketplace 条款："Marketplace Offerings are intended for use only with Visual Studio Products and Services"。Remote 扩展（SSH、Containers、WSL）和 Live Share 是闭源的，code-server 里用不了 — [code-server FAQ](https://coder.com/docs/code-server/FAQ)
- Remote-SSH 的许可链接是 go.microsoft.com/fwlink/?linkid=2077057，扩展页没写是否开源 — [Marketplace: Remote - SSH](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-ssh)
- 在 Cursor 里装微软扩展会报 "Remote - SSH is only supported in Microsoft versions of VS Code" — [Cursor Forum](https://forum.cursor.com/t/remote-ssh-is-only-supported-in-microsoft-versions-of-vs-code/23918)。VSCodium 社区的替代方案是开源的 `jeanp413.open-remote-ssh` — [VSCodium Discussion #693](https://github.com/VSCodium/vscodium/discussions/693)；[coder/vscode-coder#408](https://github.com/coder/vscode-coder/issues/408)

**与宿主上的 Claude Code 共存（重要坑）**
- Claude Code VS Code 扩展在 Remote SSH 下每次都要求重新登录，原因是 macOS Keychain 在 SSH 会话里无法访问 — [anthropics/claude-code#44089](https://github.com/anthropics/claude-code/issues/44089)。CLI 在 SSH 下也有同样问题 — [anthropics/claude-code#29816](https://github.com/anthropics/claude-code/issues/29816)（解决办法见 Q8）

### Inferences
- 对"宿主上 Agent 改文件、笔记本上审阅"的场景，VS Code Remote-SSH 是最成熟的选项。文件监听、git（SCM 视图、diff 编辑器）、搜索、LSP 都在宿主上运行，Agent 写盘后编辑器马上能看到，没有同步层带来的冲突。风险只在于编辑器里未保存的 buffer 和 Agent 同时改同一个文件。
- 敲键和渲染都在本地，延迟只影响补全、跳转、打开和保存，所以对 Tailscale 经 DERP 中继的几十到上百毫秒并不敏感（见 Q8）。
- Tunnels 适合"没法 SSH"或"从浏览器 vscode.dev 临时访问"的情况。但它依赖微软中继和账号，且有 10 条 tunnel 的上限；已经有 Tailscale 时没什么必要用。
- macOS 宿主上，VS Code Server 的 node 进程由 sshd 派生。如果仓库放在 `~/Documents` 或 `~/Desktop` 这类 TCC 保护目录，需要在宿主的"远程登录"里开启"允许远程用户完全磁盘访问"（见 Q8）。本项目路径正是 `~/Documents/herdr`，要特别注意。

### Gaps
- 没抓到 VS Code 官方文档中 `remote.autoForwardPorts` 的完整描述，上面的细节来自 release notes 和 issue。
- 没查到 2026 年 VS Code Remote-SSH 针对 macOS 26 宿主的已知问题清单。

## Q2. Cursor Remote-SSH（以及 Windsurf）

### Takeaway
Cursor 因为许可限制，不能用微软的 Remote-SSH，改用自研的 `anysphere.remote-ssh`，架构与 VS Code 相同：UI 在本地，终端、调试和 Agent 的工具执行都在宿主上。2026 年论坛上有较多回归问题：v1.0.51 导致无法连接、macOS 26 上反复提示安装扩展、Agent Shell 工具丢失完成信号等。可以用，但可靠性明显不如 VS Code 官方实现。Windsurf 同样是自研 SSH。

### Cited Findings
- Cursor 的 Remote-SSH 流程是本地跑 UI，远端执行终端、调试器和进程。与 VS Code 共用同一份 SSH config — [KodeKloud: Cursor Remote Development](https://notes.kodekloud.com/docs/Cursor-AI/Understanding-and-Customizing-Cursor/Demo-Remote-Development/page)；[Harvard FAS RC: Cursor remote via SSH and tunnel](https://docs.rc.fas.harvard.edu/kb/cursor-remote-development-via-ssh-and-tunnel)
- Cursor 官方 wiki 称 Remote-SSH 扩展"can be used to connect from any client platform to a macOS remote" — [anysphere/cursor-wiki Sanity-Check](https://github.com/anysphere/cursor-wiki/blob/main/Sanity-Check.md)
- **2026 回归**：anysphere.remote-ssh 在 2026-05-22 自动更新到 1.0.51 后，"Connect to Host" 完全失效 — [Cursor Forum #161341](https://forum.cursor.com/t/bug-report-remote-ssh-extension-v1-0-51-breaks-connect-to-host/161341)
- **macOS 26 专属 bug**：已装 anysphere.remote-ssh，但 Cursor 检查的是 ms-vscode-remote.remote-ssh 的 ID，导致每次启动都弹提示 — [Cursor Forum #160607](https://forum.cursor.com/t/macos-26-remote-ssh-extension-prompt-loop-on-every-startup-anysphere-remote-ssh-installed-but-ms-vscode-remote-remote-ssh-id-checked/160607)（只看到标题，正文抓取被拦截）
- Anysphere 版本在非交互式终端中运行，交互式认证流程可能用不了 — [Cursor Forum #116718](https://forum.cursor.com/t/anysphere-remote-ssh-plugin-does-not-support-interactive-terminal-sessions/116718)
- 多个 Agent 在 Remote SSH 工作区做大范围代码搜索时，另一个 Agent 的 Shell 工具会丢失命令完成信号 — [Cursor Forum #160918](https://forum.cursor.com/t/remote-ssh-agent-shell-tool-loses-completion-under-concurrent-code-search-load/160918)。社区有 "Durable agent runtime on Remote SSH" 的功能请求 — [Cursor Forum #159513](https://forum.cursor.com/t/durable-agent-runtime-on-remote-ssh-cloud-workstations/159513)
- 通过 SSH 连接时，Cursor 不能分析笔记本本地的文档，文件要先上传到远端 — [Cursor Forum #168451](https://forum.cursor.com/t/cursor-cannot-analyze-local-documents-when-connected-via-ssh-files-must-be-uploaded-to-the-remote-server/168451)（仅标题）
- 二手评测（2026-09-15）：Cursor "rebuilt its own remote-connection layer"，并称其"a noticeably higher rate of connection drops, stalled file syncs, and occasional 404 errors when reconnecting"。SSH 加 Dev Container 的组合最容易失败。免费 Hobby 档对 Tab 和 Agent 请求的限额较严 — [tech-insider.org](https://tech-insider.org/vs-code-vs-cursor-remote-development-ssh-containers-2026/)（二手来源，未见量化数据，谨慎引用）
- Windsurf："implements its own SSH support because the usual SSH support in VSCode is licensed by Microsoft"，需要 OpenSSH — [Windsurf Docs: Advanced](https://codeium.mintlify.app/windsurf/advanced)；[Markaicode 2026](https://markaicode.com/windsurf-remote-development-ssh-containers/)

### Inferences
- Cursor 的 Agent 在 Remote SSH 下对工作区执行工具调用（改文件、跑命令），这些都发生在宿主上。结合 #159513 的诉求，Agent 会话的运行时很可能跟笔记本上的 Cursor 窗口绑定：笔记本合盖或断线后，Agent 不会像 herdr 里的 Claude Code 那样持续运行。所以 Cursor 更适合做编辑器和审阅器，长时间运行的 Agent 仍交给 herdr。
- 如果同时装了 Cursor 和 VS Code，两者在宿主上各装一份 server（~/.cursor-server 与 ~/.vscode-server），互不冲突，但会各占内存和磁盘。
- 建议关闭 Cursor 远程扩展的自动更新，或锁定已知可用的版本，避免遇到 1.0.51 这类回归。

### Gaps
- 没找到 Cursor 官方文档里关于"AI 请求从客户端还是宿主发出"以及"代码库索引在哪一侧计算"的一手说明。cursor.com/docs 本轮没抓到对应页面。
- Windsurf 在 2025 年被收购、2026 年产品状态变化后，远程 SSH 的现状本轮没有核实。
- Cursor 远程扩展的许可条款没查到。

## Q3. JetBrains Gateway / JetBrains 远程开发（Toolbox App）

### Takeaway
JetBrains 远程开发是"后端 IDE 跑在宿主，本地 JetBrains Client 做瘦客户端"。关键限制是：**通过 Gateway 连接时后端只支持 Linux**，要以 macOS 为宿主必须用 **Toolbox App 2.6+ 的远程开发功能**（2025-04 发布，支持 Linux、Windows、macOS 宿主）。2026-09 文档中 Gateway 仍然在维护。

### Cited Findings
- 架构："The remote host ... hosting the source code and running a backend IDE. You connect to the backend that transparently provides full access to all IDE features"。后端插件提供的检查和功能都会显示在 JetBrains Client 中。JetBrains Client "is not designed to be extensible for the connection part" — [IntelliJ IDEA Docs: Remote development overview (2026.2, 2026-09-07)](https://www.jetbrains.com/help/idea/remote-development-overview.html)
- Gateway 在 2026.2 文档中仍是当前工具，支持 WSL、Codespaces 等 — [同上](https://www.jetbrains.com/help/idea/remote-development-overview.html)
- **macOS 宿主**：用 Gateway 连接时后端只支持 Linux 服务器，用 Toolbox App 则 macOS 和 Windows 服务器也支持 — [IntelliJ IDEA FAQ about remote development（经搜索摘要，页面本身抓取被拦截）](https://www.jetbrains.com/help/idea/faq-about-remote-development.html)；相关 YouTrack：[IJPL-170306 "Remote development host should be available on macOS and Windows"](https://youtrack.jetbrains.com/projects/IJPL/issues/IJPL-170306/Remote-development-host-should-be-available-on-macOS-and-Windows)
- Toolbox App 2.6（2025-04）："connect to different host platforms, including Windows, macOS, and Linux"。使用 OpenSSH，支持 ProxyJump、MFA、IdentityFile、askpass，也可以替换 SSH 二进制；可以导入现有 SSH config 和 Gateway 配置；"if it works in the terminal, it'll work in the Toolbox App, too"；推荐 IDE 版本 2025.1+ — [JetBrains Blog: Toolbox App 2.6](https://blog.jetbrains.com/toolbox-app/2025/04/toolbox-app-2-6-is-here-with-remote-development-support/)
- 不支持的宿主类型：树莓派等单板机、共享虚拟主机 — [IntelliJ IDEA Docs: prerequisites](https://www.jetbrains.com/help/idea/prerequisites.html)

### Inferences
- 在 Apple silicon + macOS 26 宿主上应走 Toolbox App 远程开发，不要走 Gateway。因为后端直接读宿主磁盘，Agent 的外部修改会通过后端的 VFS 刷新反映出来，但刷新时机和冲突提示的行为本轮没有核实。
- 后端是一个完整的 IDE 进程，内存占用明显高于 VS Code Server 或 Zed remote_server。宿主同时跑多个 Agent 时要预留内存。
- 同样受宿主 TCC 限制（`~/Documents`）和 PATH 解析方式的影响（见 Q8）。

### Gaps
- 许可：后端和客户端需要哪种许可、是否需要付费 IDE 订阅，本轮没抓到官方说明（FAQ 页被拦截）。
- JetBrains 远程开发的端口转发、延迟补偿（客户端本地编辑）机制，以及 macOS 后端是否仍标为 Beta，都没有核实。
- 2026 年 Gateway 是否会被 Toolbox 完全取代，没有官方公告。

## Q4. Zed 远程开发（`zed ssh://host/path`）

### Takeaway
Zed 的 UI、Tree-sitter 语法解析、LLM 调用和**未保存的修改**都在本地，源码、LSP、任务和终端都在宿主上（`remote_server` 二进制）。官方支持 macOS Catalina 以上（含 Apple silicon）作为宿主。内置 Agent Panel 在远程会话中可用。通过 ACP 接入外部 Agent（Claude Code 等）的做法在 SSH 场景下仍有断线后无法恢复等问题。

### Cited Findings
- 分工：本地 "runs its UI, talks to language models, uses Tree-sitter ... and stores unsaved changes"；远端 "The source code, language servers, tasks, and the terminal all run on the remote server" — [Zed Docs: Remote Development](https://zed.dev/docs/remote-development)
- 宿主支持："macOS Catalina or later (Intel or Apple Silicon)"、Linux x86_64/arm64、Windows — [同上](https://zed.dev/docs/remote-development)
- 连接方式：`ctrl-cmd-shift-o` 打开 Remote Projects；命令行 `zed ssh://[<user>@]<host>[:<port>]/<path>`；deep link `zed://ssh/...` — [同上](https://zed.dev/docs/remote-development)
- server 二进制默认由宿主直接从 zed.dev 下载。可以设为先下载到笔记本再经 SSH 上传（适合宿主不能联网的情况）。也可以自己编译后放到 `~/.zed_server/`，版本要精确匹配 — [同上](https://zed.dev/docs/remote-development)
- 设置分三层：本地设置管 UI，server 设置管 LSP 路径和代理，项目设置两端都读。"they are not aware of the other's main settings file" — [同上](https://zed.dev/docs/remote-development)
- 端口转发：`"port_forwards": [{"local_port": 8080, "remote_port": 80}]`，默认绑定 localhost，可以设 `local_host` 为 `0.0.0.0` — [同上](https://zed.dev/docs/remote-development)
- 扩展："Any extensions you have installed locally will be propagated to the remote server"。AI："AI features work in remote sessions, including the Agent Panel and Inline Assistant" — [同上](https://zed.dev/docs/remote-development)
- 限制：远程终端里不能用 `zed` 命令打开文件。超过 100,000 个文件的大目录性能很差，建议打开具体项目目录。需要 v0.159+（旧的经 Zed 服务器中转的模式从 v0.157 起弃用）— [同上](https://zed.dev/docs/remote-development)
- 外部 Agent（ACP）与 SSH：Agent 可能在本地、远端或通过自己的登录流程读取凭据，"Check the specific agent's setup path when using SSH" — [Zed Docs: External Agents](https://zed.dev/docs/ai/external-agents)。SSH 断开后 ACP Agent 线程丢失，重连报 "Failed to Launch" — [zed#60213](https://github.com/zed-industries/zed/issues/60213)。Zed 1.15.0 导入 Claude Code SSH 会话时丢失 SSH 元数据，被当成本地线程 — [zed#62721](https://github.com/zed-industries/zed/issues/62721)。在 Zed 中通过 claude-acp 运行的 Claude Code 不能用 Remote Control — [zed#61996](https://github.com/zed-industries/zed/issues/61996)

### Inferences
- Zed 是原生 GPU 渲染的编辑器，未保存的修改保存在本地。SSH 抖动时本地打字不受影响，适合 Tailscale 外网场景。它的原生 git diff 和多 buffer 视图，适合审阅 Agent 产出的改动。
- 长时间运行的 Agent 仍建议放在 herdr（宿主上的持久会话）中，Zed 只做编辑和审阅，避免 SSH 断开时丢失 ACP 线程（#60213）。
- 大 monorepo 中 Agent 生成的 `node_modules`、构建产物会拖慢扫描，应该只打开子项目或加排除规则。
- 从 issue 编号和 "Zed 1.15.0" 看，Zed 在 2026 年已经发布 1.x 版本。以上文档描述都是当前版本。

### Gaps
- Zed 定价（编辑器免费、AI 计划收费）本轮没有抓取核实。
- Zed remote_server 在 macOS 宿主上如何解析 PATH（是否用 login shell），文档中没找到。

## Q5. 浏览器方案：code-server（Coder）、openvscode-server（Gitpod），通过 Tailscale Serve 暴露

### Takeaway
在宿主上跑一个 Web 版 VS Code，笔记本用浏览器访问，本地什么都不用装，iPad 也能用。代价是：只能用 Open VSX 扩展（没有微软 Remote、Live Share 以及部分闭源扩展），webview 需要 HTTPS 安全上下文，浏览器快捷键可能冲突，macOS 上还要给 node 授予完全磁盘访问权限。`tailscale serve` 可以提供只在 tailnet 内可访问的 HTTPS 和身份头，是最干净的暴露方式。

### Cited Findings
- code-server 采用 MIT 许可。由于 "Microsoft prohibits the use of any non-Microsoft VS Code from accessing their marketplace"，它使用 Open VSX。Live Share 和 Remote（SSH/Containers/WSL）不可用 — [code-server FAQ](https://coder.com/docs/code-server/FAQ)；[coder/code-server](https://github.com/coder/code-server)
- Webview "are only available in a secure context"，需要 HTTPS、受信证书或 localhost，否则会报 service worker 错误 — [code-server FAQ](https://coder.com/docs/code-server/FAQ)
- **macOS 宿主**：新版 macOS 上需要"Grant Node.js full disk access"才能访问 Documents、Downloads、Desktop — [code-server FAQ](https://coder.com/docs/code-server/FAQ)
- 与 openvscode-server 的区别：code-server "contains additional changes to make the self-hosted experience better"（密码认证、子路径托管、遥测选项）。如果需要官方 Marketplace，VS Code Web 可能更合适 — [code-server FAQ](https://coder.com/docs/code-server/FAQ)
- openvscode-server：MIT，使用 Open VSX，`--connection-token` / `--connection-token-file` 控制访问，远程访问时建议 `--host 0.0.0.0`。"only adds minimal bits required to run VS Code in a server scenario"。README 只给出 Linux 发布包 — [gitpod-io/openvscode-server](https://github.com/gitpod-io/openvscode-server)
- Tailscale Serve：只在 tailnet 内可访问的反向代理，例如 `tailscale serve 3000`；需要在 tailnet 启用 HTTPS 证书。会注入 `Tailscale-User-Login` / `Tailscale-User-Name` 等身份头。要公开到互联网才用 Funnel。**在 macOS 上**，"Serving files and directories is limited to the open source variant of the Tailscale client"（App Store 版受沙箱限制），反向代理本地端口不受这个限制 — [Tailscale Docs: Serve](https://tailscale.com/kb/1312/serve)
- Tailscale 官方有 code-server 加 Caddy 的 iPad 方案示例 — [Tailscale Docs: Code on iPad](https://tailscale.com/docs/solutions/code-on-ipad-vscode-caddy-code-server)

### Inferences
- 推荐拓扑：code-server 只绑定 `127.0.0.1:8080`（开启密码或关闭认证都可以），然后 `tailscale serve --bg 8080` 暴露为 `https://<host>.<tailnet>.ts.net`。这样既满足 webview 的安全上下文要求，又不在 LAN 上开放端口。不要用 Funnel。
- 如果用 launchd 常驻 code-server，TCC 授权对象是 node 可执行文件（或其父进程），与从 SSH 启动时不同，两种都要验证能否访问 `~/Documents`。
- 浏览器方案的延迟特性和 VS Code Remote 类似（UI 在本地浏览器），但 Cmd+W、Cmd+T 等快捷键会被浏览器抢占。建议装成 PWA 独立窗口使用。
- 相比 Remote-SSH，唯一的独特价值是"不装客户端、任何设备都能访问（包括 iPad）"。如果笔记本上已经有 VS Code 或 Zed，浏览器方案的优先级较低。

### Gaps
- code-server 和 openvscode-server 2026 年的最新版本号及发布日期没有抓到。openvscode-server 在 Gitpod 更名为 Ona 后是否仍积极维护，没有找到确切证据。
- macOS 原生安装方式（如 Homebrew）本轮没有抓取核实。
- Copilot、Claude Code 等 AI 扩展在 Open VSX 上的可用性没有逐一核实。

## Q6. 终端原生方案（在 herdr 里用 Neovim/Helix）与基于 Git 的审阅流程

### Takeaway
最省事的方案是：在 herdr 中开一个 pane，直接在宿主上跑 Neovim 或 Helix、lazygit、`git diff | delta`，不需要任何额外服务。审阅时用 `git worktree` 为每个 Agent 隔离工作目录，再用 `gh` 或 GitHub PR 网页作为正式的审阅界面。缺点是每次按键都要往返一次网络，用 mosh 可以缓解。GitHub Desktop 这类本地 GUI 不能直接操作远端仓库。

### Cited Findings
- 已有 herdr 加 Mac mini 的实践（2026-08-07）：herdr server 常驻，"panes, agents keep running even after you detach the client"。笔记本经 Tailscale 加 SSH 连接，通过 SSH 转发 herdr 的 Unix socket 来执行 CLI。手机用 mosh（UDP）。`claude-on-worktree` 插件在创建 workspace 时自动启动 Claude Code，插件需要在每台机器上执行 `herdr plugin link`。嵌套 herdr 默认禁用，需要 `allow_nested = true`。多个客户端同时 attach 时"display area is adjusted to the smallest client" — [DevelopersIO (classmethod): herdr remote Mac mini](https://dev.classmethod.jp/en/articles/reona-herdr-remote-mac-mini/)

### Inferences
（以下工具的功能描述是常识，本轮没有逐一抓取官方页面，链接供查证）
- Neovim（[neovim.io](https://neovim.io)）和 Helix（[helix-editor.com](https://helix-editor.com)）都是纯终端程序，LSP 和文件监听全在宿主上。与 herdr 的 pane 或窗口天然融合，不需要端口、扩展或 TCC 额外授权（仍受 SSH 会话 TCC 影响，见 Q8）。

- 延迟敏感度：终端方案每次按键都要网络往返。Tailscale 直连时几乎无感；走 DERP 中继（50–200ms，见 Q8）时，Neovim 或 Helix 的输入回显会明显滞后。mosh 可以做本地回显预测，但它与 herdr 自己的会话管理叠加时要注意屏幕尺寸协商（classmethod 文提到按最小客户端调整）。

## Q7. 单窗口 / 单应用转发（macOS 原生 GUI）以及 iOS Simulator / Xcode

### Takeaway
在 macOS 宿主上，**目前没有成熟方案能把某一个原生 Cocoa 窗口"无缝"转发到另一台 Mac**。X11 转发只对 X11 程序有效，Xpra 在 macOS 上只有整屏 shadow 模式，Apple 屏幕共享只能共享整个屏幕，Jump Desktop 只能按显示器切分（单应用窗口仍停留在社区功能请求），Microsoft RemoteApp 只支持 Windows。对 Xcode 和 Simulator，现实做法是：在宿主上用 `xcodebuild` / `simctl` 无头构建和截图，或者用 xcode-remote 这类工具把构建出的 .app 通过 SSH 送到笔记本上运行；需要看界面时再退回整屏共享。

### Cited Findings
- Xpra："On X11 ... it allows you to run programs, usually on a remote host, direct their display to your local machine"（无缝的单窗口模式）；对 MS Windows 和 Mac OS X 只提到 "forward full desktops" — [xpra.org](https://xpra.org/index.html)
- Xpra shadow："It works with Linux, macOS, and Windows servers"。macOS 上没有 X11 display name。存在已知问题 #391（macOS shadow server improvements）、#1321（滚动）、#1322（缩放）。文档只描述整桌面 shadow，没有单窗口 shadow — [Xpra Docs: Shadow](https://raw.githubusercontent.com/Xpra-org/xpra/master/docs/Usage/Shadow.md)。可以 shadow 某个区域或某个显示器，但"On most MS Windows and MacOS systems, starting shadow servers via SSH is not supported"，需要在宿主 GUI 会话里手动启动 — [xpra manual](https://xpra.org/manual)；[Arch man xpra(1)](https://man.archlinux.org/man/xpra.1.en)（**与 Shadow.md 中通用的 `xpra shadow ssh://HOST/` 写法有冲突，macOS 上以 manual 为准，需要实测**）
- Apple 屏幕共享：内置 Screen Sharing 只能共享整个屏幕，不能选单个应用窗口 — [MacRumors Forum](https://forums.macrumors.com/threads/mac-screen-sharing-limited-to-specific-app-window.1644755/)；[Airtame KB](https://help.airtame.com/hc/en-us/articles/5309802647965-Single-window-sharing-for-Windows-and-macOS)（二手来源）；Apple 官方文档：[Share the screen of another Mac](https://support.apple.com/en-au/guide/mac-help/mh14066)
- Jump Desktop：提供 "All Displays" 单窗口模式（把所有远程显示器合成到一个窗口）和 "Displays in Separate Windows"，都是按显示器而不是按应用 — [Jump Desktop Changelog](https://changelog.jumpdesktop.com/)。"只共享单个 Mac 应用窗口、像本地应用一样显示"是社区功能请求 — [Jump Desktop Community: Feature request](https://support.jumpdesktop.com/hc/en-us/community/posts/360061662872-Feature-request-Share-only-window-from-a-single-app)（页面 403，官方回复未知）
- 技术底座：ScreenCaptureKit 支持用 `SCContentFilter`（desktopIndependentWindow）只采集单个窗口，但网络传输和输入注入要自己实现 — [Apple Developer: ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)；[WWDC22 10155](https://developer.apple.com/videos/play/wwdc2022/10155/)
- 无头宿主的显示问题（博客观点）：没有显示器时 "macOS degrades — GPU acceleration drops, Screen Sharing fails"，建议插 HDMI 假负载 — [Jesse Meria 2026](https://jessemeria.com/blog/mac-mini-remote-dev-server)
- **Xcode / Simulator**：xcode-remote（2026-07-08）在无头构建机上 `xcodebuild`，把 `.app` 通过 SSH 拷到"我正在看的那台机器"，再用 `open`（macOS）、`simctl`（模拟器）或 `devicectl`（真机）启动，并以 JSON 返回构建状态、PID、日志和崩溃报告。签名用 fastlane match 手动签名，绕过依赖 GUI 的账号枚举。作者提到 Agent 可以"boot a simulator headlessly and screenshot it" — [Evan Coleman: Introducing xcode-remote](https://edc.me/posts/introducing-xcode-remote/)；[blackpaw-studio/xcode-remote](https://github.com/blackpaw-studio/xcode-remote)
- 用于驱动模拟器的 MCP 服务器（截图、UI 树、点击、应用生命周期）— [mgcrea/mcp-ios-simulator](https://github.com/mgcrea/mcp-ios-simulator)
- 远程 Mac mini 上 `xcodebuild` 可以完全无头运行，需要 GUI 时再加 VNC — [ZecCloud 2026](https://zeccloud.com/en/blog/articles/mac-mini-m4-ssh-remote-access-guide-2026.html)（商业博客）

### Inferences
- **为什么 X11 转发（ssh -X 加 XQuartz）不适用**：XQuartz 只是 macOS 上的 X11 服务器，只能显示 X11 协议的客户端程序。原生 Cocoa/AppKit/SwiftUI 应用直接经 WindowServer（Quartz Compositor）绘制，从不发出 X11 请求，所以 `ssh -X` 对它们无效。这属于平台常识，本轮没有抓取 Apple 或 XQuartz 的原文。
- Microsoft RemoteApp（RDS / AVD 的 RemoteApp 发布）要求宿主是 Windows，对 macOS 宿主不适用。这是常识，本轮没有抓取微软文档。
- TeamViewer 等会议或远程工具的"选择应用共享"一般是只读演示用途，不等于可交互的无缝单窗口远程。本轮没有核实。
- 对本场景的实际建议：GUI 只在必要时用整屏共享（macOS 屏幕共享的高性能模式、Jump Desktop Fluid 等，属另一份调研范围），并配合宿主插 HDMI 假负载或设置虚拟显示器。日常代码审阅完全不需要窗口转发。
- iOS 相关：让 Agent 在宿主上跑 `xcodebuild test` 和 `xcrun simctl boot` / `io <udid> screenshot`，截图文件再用 scp 取回或在编辑器远程会话里直接打开 PNG。`simctl io screenshot` 的输出行为有坑：有报告说它写文件、信息打到 stderr，而不是 help 文本所说的 stdout。来源不明确，需要实测。

## Q8. 跨方案通用：macOS 宿主的坑（PATH、Keychain、TCC、睡眠）、LAN 与 Tailscale 的差异、与 AI Agent 的共存、安全

### Takeaway
macOS 宿主有三大坑：①非交互式 SSH 的环境与交互式 shell 不同；②SSH 会话里 login Keychain 是锁定的，Claude Code 等基于 OAuth 的 Agent 会反复要求登录；③TCC 保护 `~/Documents`、`~/Desktop`，经 sshd 派生的 server 进程访问不了，必须在"远程登录"里开启"允许远程用户完全磁盘访问"。网络方面，Tailscale 直连与同 LAN 体验接近，走 DERP 中继时会多出几十到上百毫秒，对终端方案影响最大，对本地渲染 UI 的编辑器影响最小。

### Cited Findings
**TCC / 完全磁盘访问**
- 系统设置 > 通用 > 共享 > 远程登录（点 ⓘ）中有 "Allow full disk access for remote users"。该选项通常只能由坐在该 Mac 前的登录用户开启，也可以用 MDM 配置描述文件下发 — [Apple Support: Allow a remote computer to access your Mac (macOS 26)](https://support.apple.com/en-bn/guide/mac-help/allow-a-remote-computer-to-access-your-mac-mchlp1066/26/mac/26)；[Michael Tsai blog](https://mjtsai.com/blog/2023/04/28/allowing-a-remote-computer-to-access-your-mac/)；[Der Flounder: FDA for SSH via profile](https://derflounder.wordpress.com/2021/09/29/enabling-full-disk-access-for-ssh-on-macos-big-sur-using-a-management-profile/)
- 非 GUI 的 SSH 会话不会继承交互式 Terminal 已经获得的 TCC 授权 — [Daniel Cosenza: Enabling and Hardening Remote Login](https://danielcosenza.com/posts/mac-howto-ssh-remote-login/)
- code-server 在 macOS 上要给 Node.js 完全磁盘访问才能读 Documents、Downloads、Desktop — [code-server FAQ](https://coder.com/docs/code-server/FAQ)

**Keychain**
- SSH 会话中 login keychain 是锁定的，Claude Code 读不到 OAuth token。解决办法：`security unlock-keychain ~/Library/Keychains/login.keychain-db`；写一个每会话只解锁一次的 wrapper；利用 `~/.claude/.credentials.json` 文件回退；宿主开启自动登录，让 loginwindow 在开机时解锁 keychain — [phoenixtrap.com (2025-10)](https://phoenixtrap.com/2025/10/26/claude-code-cli-over-ssh-on-macos-fixing-keychain-access/)；[thekodelab](https://thekodelab.com/en/posts/macos-ssh-keychain-unlock/)；[anthropics/claude-code#9403](https://github.com/anthropics/claude-code/issues/9403)；[#29816](https://github.com/anthropics/claude-code/issues/29816)
- herdr 加 Mac mini 实践同样记录了 "SSH sessions don't have permission to write to the keychain" — [DevelopersIO](https://dev.classmethod.jp/en/articles/reona-herdr-remote-mac-mini/)
- VS Code Remote SSH 中的 Claude Code 扩展也受影响 — [anthropics/claude-code#44089](https://github.com/anthropics/claude-code/issues/44089)

**PATH**
- VS Code Server 用 interactive login shell 解析环境 — [VS Code Docs: Troubleshooting](https://code.visualstudio.com/docs/remote/troubleshooting)

**睡眠 / 无头**
- 设置"防止自动睡眠"、"网络唤醒"、"断电后自动启动"，插 HDMI 假负载，用 launchd 在重启后恢复会话 — [Jesse Meria 2026](https://jessemeria.com/blog/mac-mini-remote-dev-server)

**LAN vs Tailscale**
- 所有连接先经 DERP 中继建立，然后尝试升级为直连，失败时尝试 peer relay，再失败就一直走 DERP — [Tailscale Docs: Connection types](https://tailscale.com/docs/reference/connection-types)；[Peer Relays](https://tailscale.com/docs/features/peer-relay)
- 用 `tailscale ping <host>` 查看连接类型：输出 "via DERP(xxx)" 表示中继，"via <ip>:<port>" 表示直连。同一大洲内直连约 5–30ms，中继约 50–200ms — [SSD Nodes](https://www.ssdnodes.com/learn/tailscale-slow-direct-vs-relayed)（二手来源，数值是经验范围）

**安全**
- SSH 加固建议：只允许密钥登录（`PasswordAuthentication no` 等）— [Jesse Meria 2026](https://jessemeria.com/blog/mac-mini-remote-dev-server)
- VS Code Tunnels 不开监听端口，用 AES-256-CTR 加密，账号认证 — [VS Code Docs: Tunnels](https://code.visualstudio.com/docs/remote/tunnels)
- Zed 的端口转发默认只绑定 localhost — [Zed Docs](https://zed.dev/docs/remote-development)
- Tailscale Serve 只在 tailnet 内可访问并带身份头，Funnel 才是公网 — [Tailscale Docs: Serve](https://tailscale.com/kb/1312/serve)

### Inferences
- **PATH 规则**（zsh 常识，未抓取原文）：`ssh host cmd` 是非交互、非 login 的 zsh，只读 `~/.zshenv`，不读 `~/.zprofile` 和 `~/.zshrc`。Homebrew（`/opt/homebrew/bin`）以及 Agent CLI（`claude`、`codex`、node 版本管理器）通常只在 `.zprofile` 或 `.zshrc` 里加入 PATH。所以 `ssh host herdr ...` 这类命令可能出现 "command not found"。解决办法：把关键的 PATH 放进 `~/.zshenv`，或调用时用 `zsh -lc '...'`。VS Code Server 用 login shell，基本不受影响。Zed 和 JetBrains 的行为需要实测。
- **TCC 与项目路径**：本项目位于 `~/Documents/herdr`。VS Code Server、Zed remote_server、JetBrains 后端都是 sshd 的子进程，不开"允许远程用户完全磁盘访问"就会报 "Operation not permitted" 或看到空目录。最简单的规避办法是把代码仓库放在 `~/Code` 或 `~/src` 这类非 TCC 保护目录，就不必给所有 SSH 会话放开 FDA（安全面更小）。
- **与 AI Agent 共存**：以上所有远程编辑器方案（VS Code、Cursor、Zed、JetBrains、code-server、nvim）都直接读写宿主磁盘，文件监听（FSEvents）和 git 都在宿主本地运行。Agent 的改动能即时反映，不存在两份副本的同步冲突。主要风险有三点：①编辑器里有未保存的 buffer，Agent 同时改了同一个文件（Zed 会把未保存修改保存在本地）；②编辑器的 git 自动 fetch 或暂存，与 Agent 的 git 操作争抢 `.git/index.lock`；③Agent 同时启动的多个 dev server 触发 VS Code 超过 20 个端口的自动转发问题。建议每个 Agent 一个 worktree，编辑器只打开需要审阅的 worktree，关闭自动 fetch，限制自动转发。
- **延迟敏感度排序**（从高到低）：整屏共享 > 终端编辑（nvim/Helix 在 herdr 中）> JetBrains 瘦客户端 ≈ 浏览器 code-server ≈ VS Code/Cursor/Zed Remote（本地渲染和本地回显）> Git/PR 网页审阅（与连接质量无关）。
- **LAN vs Tailscale**：同一 LAN 下 Tailscale 通常能打出直连，与直接用 LAN IP 差别很小，还带来稳定的 MagicDNS 名称和 ACL，所以建议统一用 Tailscale 主机名写 `~/.ssh/config`。在外网时要先确认 `tailscale ping` 是直连。
- Tailscale SSH（由 tailscaled 代替 sshd 接管）在 macOS 上的可用性依赖客户端版本（开源 tailscaled 与 App Store/独立 App 不同）。本轮没有核实，建议继续使用系统 sshd（远程登录）。

### Gaps
- 没有抓到 Tailscale 官方文档中直连与中继的具体延迟数字（官方连接类型页抓取超时，数值来自二手博客）。
- macOS 26 在 TCC 或远程登录上是否有新变化，没有找到专门资料。
- Tailscale SSH 在 macOS 各客户端变体上的支持情况没有核实。

## Q9. 不远程运行编辑器：挂载宿主文件系统 + 本地编辑器（简述，文件层另有专题）

### Takeaway
用 SSHFS/macFUSE、SMB 等把宿主目录挂到笔记本，再用本地编辑器打开，看起来"最原生"。但 LSP、构建和 git 都会在笔记本上通过网络文件系统运行，性能差；文件监听跨网络文件系统也不可靠；工具链还要两端都装。与"宿主上多个 Agent 高频写文件"的场景很不匹配，只建议偶尔查看文件时使用。

### Cited Findings
- 远程编辑器方案与此的核心区别：Zed 明确把 "source code, language servers, tasks, and the terminal" 放在宿主上 — [Zed Docs](https://zed.dev/docs/remote-development)；VS Code 把大多数扩展（含 LSP）放在宿主上 — [VS Code Docs: Remote SSH](https://code.visualstudio.com/docs/remote/ssh)
- 反例：Cursor 连 SSH 时不能直接分析笔记本本地文件，说明远程模式下"文件在哪一侧"是硬边界 — [Cursor Forum #168451](https://forum.cursor.com/t/cursor-cannot-analyze-local-documents-when-connected-via-ssh-files-must-be-uploaded-to-the-remote-server/168451)

### Inferences
- 在网络文件系统上，FSEvents 通知通常不能跨机器传递，编辑器难以及时感知 Agent 的改动。git status、全文搜索、索引会产生大量小文件 I/O，经 Tailscale 时很慢。挂载断开时编辑器可能卡死。这些是常识性推断，本轮没有抓取资料。
- 如果一定要本地编辑，更稳的是 git 层同步：宿主推分支，笔记本 fetch 或 checkout 后审阅；或者用双向同步工具（属文件层专题）。

### Gaps
- SSHFS/macFUSE 在 macOS 26 上的现状（内核扩展与 FSKit 迁移）不在本专题范围，本轮没有调研。
